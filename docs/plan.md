# 멀티 AI 주식 리서치 시스템 기획서

> 상태: 초안 v4 / 개정 2026-09-14
> 접근: **기존 시스템 평가 → 자체 구축**
> 시장: **미국장 + 한국장 각 1개 인스턴스**
> LLM: **DeepSeek 확정** (4절)
> 운용 범위: **실계좌 주문 없음. 시그널 기록 + 가상 보유 포트폴리오 추적만.**

---

## 0. 원칙

1. 목표는 "수익률 극대화"가 아니라 **다양한 관점의 구조화된 의견 생성과 그 검증**
2. 어떤 결론도 투자 자문이 아님. 실행 판단은 사람이 별도로.
3. **"성능 좋은 것"을 말하려면 먼저 공정한 저울(백테스트 하네스)이 있어야 한다.** 이게 이 프로젝트의 실제 1순위 산출물.
4. 평가 단위는 **포트폴리오 수익률이 아니라 개별 시그널**. 이유는 9.3절.

```
Phase A (4~5주)  기존 시스템 평가

Phase C (3개월~) 시그널 기록 + 가상 보유 추적
```

**핵심 자원: 코스콤 로보어드바이저 테스트베드.** 2016년부터 운영되는 공적 검증 인프라로, 43개 금융사의 알고리즘 수백 개(2026년 기준 380~438개)에 대해 **동일 조건 수익률을 공시**한다. 국내에 이런 표준화 공시가 존재한다는 건 우리 프로젝트에 큰 이점 — 한국장 벤치마크를 직접 만들 필요 없이 **알고리즘 수익률 분포 전체**를 벤치마크로 쓸 수 있다.

### 3.3 조사할 때 조심할 것

- **"2026 최고의 AI 트레이딩 툴 TOP 10" 류 글은 대부분 제휴 마케팅이다.** 순위·수익률 주장은 근거로 쓰지 말고, **기능 명세와 가격**만 취한다.
- **단일 알고리즘 체리피킹.** 업체가 홍보하는 "1년 수익률 OOO%"는 수백 개 알고리즘 중 최상위 하나인 경우가 많다. 실제로 금융당국·코스콤이 단일 알고리즘 마케팅 활용을 제한하는 방향으로 규제를 강화 중이다. **분포 전체를 봐야 한다.**
- **AI라는 단어의 범위.** 일부 서비스의 "AI"는 전통적 수학 모델이다. LLM 기반인지, 통계 모델인지, 룰 엔진인지 구분해서 기록.
- 수익률은 기간·자산군·위험등급에 따라 완전히 달라진다. **같은 기간·같은 위험등급**이 아니면 비교하지 않는다.

## 4. LLM 구성 — DeepSeek 확정

활용 LLM은 **DeepSeek API로 확정**(2026-09). 라인업과 단가는 공식 문서 기준이며, 단가는 변동하므로 **수치보다 구조(2단 모델, 캐시, 오프피크)를 규칙으로 삼는다.**

| 모델 | 컨텍스트 | 최대 출력 | 입력(캐시 히트) | 입력(캐시 미스) | 출력 |
|---|---|---|---|---|---|
| `deepseek-flash` | 1M | 384K | $0.003 / $0.006 | $0.15 / $0.30 | $0.60 / $1.20 |
| `deepseek-v4-pro` | 1M | 384K | $0.022 / $0.044 | $0.66 / $1.32 | $1.98 / $3.96 |

백만 토큰당 USD, **오프피크 / 피크**. 피크는 UTC 월~금 01:00–04:00 및 06:00–10:00 = **KST 10\~13시, 15\~19시**이고 그 외 전 시간은 반값이다. 두 모델 모두 thinking / non-thinking 모드를 지원하고 OpenAI ChatCompletions 형식과 호환된다.

### 4.1 역할 배분

8절의 "저가 모델로 1차 스크리닝 → 상위 후보만 고성능 모델" 규칙을 모델에 매핑한 것이다.

| 단계 | 모델 | 모드 |
|---|---|---|
| 1차 스크리닝 (유니버스 전 종목) | `deepseek-flash` | non-thinking |
| 분석 에이전트 (상위 후보) | `deepseek-v4-pro` | thinking |
| 논쟁 레이어 | `deepseek-v4-pro` | thinking |
| 요약·포맷 정리 | `deepseek-flash` | non-thinking |
| 리스크 판정 | **LLM 아님 — 룰 엔진** | — |

### 4.2 비용 규칙 (설계만 지키면 추가 비용 0)

- **프리픽스 캐싱.** 캐시 히트 단가가 미스보다 모델에 따라 30~50배 싸다. 시장별 시스템 프롬프트·용어 정의·스키마 설명·공통 데이터 블록을 **고정 프리픽스**로 두고 종목별 가변부를 뒤에 붙인다. 종목마다 프롬프트 순서를 흔들면 캐시가 전부 깨진다.
- **오프피크 배치.** 주 1회 시그널 생성은 KST 심야~새벽에 스케줄한다. 같은 작업이 반값이다.
- **1M이 들어간다는 것과 1M이 잘 읽힌다는 것은 다르다.** 컨텍스트가 넓다는 이유로 원문을 통째로 밀어넣지 않는다. 에이전트 간 전달은 계속 구조화 JSON으로 한다.
- 비용은 **결정 1건당 단가**로 로그에 기록한다 (5절 평가 기준 항목).

### 4.3 재현성 — 모델 버전 고정

DeepSeek는 같은 별칭 뒤에서 모델을 갱신한다. 실험 중간에 조용히 바뀌면 그 전후 비교가 무효가 된다.

- 모든 로그 항목에 **응답이 보고한 모델 버전 문자열과 호출 타임스탬프**를 기록한다
- temperature는 0 고정. 그래도 완전 결정론은 아니므로 6절대로 3회 이상 반복해 **평균이 아니라 분산까지 보고**
- 버전이 바뀐 시점은 리뷰 로그에 남기고, 그 전후 성적을 섞어서 해석하지 않는다

### 4.4 컷오프를 모른다는 문제

DeepSeek는 학습 데이터 컷오프를 공시하지 않는다. 7절의 "모델 컷오프 이후 구간만 평가" 규칙을 문자 그대로 적용할 수 없다.

- **보수적 대리 기준**: V4 프리뷰 공개일(2026-04-24) 이후 구간만 백테스트 평가 대상으로 삼는다
- **마스킹 테스트의 비중을 올린다**: 종목명·날짜를 가린 상태와 그대로 둔 상태의 성적 차이를 측정한다. 차이가 크면 그 구간 성적은 폐기한다
- 결과적으로 **전진 기록(Phase C)이 주 평가**라는 기존 결론이 더 강해진다. 백테스트는 프레임워크 비교용이지 성능 주장용이 아니다

### 4.5 베이스라인 통일

"범용 LLM 단독 판단" 벤치마크는 **DeepSeek 단일 호출(`deepseek-v4-pro`, thinking, 도구·에이전트 없음)**로 고정한다.

다른 벤더 모델을 베이스라인에 두면 "구조가 이겼나"와 "모델이 더 좋았나"가 분리되지 않는다. 모델을 고정해야 멀티에이전트 구조만이 변수가 된다. 이 베이스라인은 6절 하네스와 9.4절 벤치마크 양쪽에 동일하게 적용한다.

### 4.6 한국어 검증 (KR 착수 전 선행)

미국장 성적이 한국장으로 이어진다고 가정하지 않는다. KR 프롬프트를 쓰기 전에 별도 확인 항목을 둔다.

- DART 사업보고서·공시 원문 발췌를 정확히 읽는가 (숫자·단위·기간 오독 여부)
- 한국 회계 표기(억/조 단위, 연결/별도, 분기 표기)를 혼동하지 않는가
- 출력에 한자·중문이 섞이지 않는가
- 실패하면 KR 전용 후처리를 두거나, **KR만 다른 모델을 쓰는 것**도 선택지로 남긴다

### 4.7 벤더 종속 완화 / 데이터 취급

- LLM 호출은 **얇은 추상화 레이어 뒤에** 둔다. OpenAI 호환이므로 base_url·모델명 교체만으로 이전 가능한 상태를 유지한다. 8절의 "에이전트 교체 가능하게"를 LLM 레이어까지 확장한 것.
- API로 보내는 것은 **공개 시장 데이터와 공시 원문뿐**이다. 계좌 정보·개인 식별 정보·타 서비스 키는 프롬프트에 넣지 않는다. 실계좌가 애초에 범위 밖이라 위험은 낮지만 규칙으로 명시한다.

## 6. 공통 백테스트 하네스 (A1)

프레임워크마다 자기 백테스트 결과를 내놓지만 조건이 달라 비교 불가. 동일 조건 러너를 먼저 만든다.

- 동일 유니버스·기간·리밸런싱 주기
- 거래비용·슬리피지 명시 (미국 편도 0.05% / 한국 편도 0.015% + 거래세 0.18%, 슬리피지 0.05%)
- **벤치마크**: 지수 buy&hold, 동일가중 랜덤 선택, **DeepSeek 단일 호출**(4.5절)
- **지표**: CAGR, MDD, Sharpe, Sortino, 승률, 턴오버, 결정당 비용
- **레짐 분리**: 상승·하락·횡보 구간 각각 따로 측정 (전체 평균은 거짓말을 함)
- **반복 실행**: 시드·모델 바꿔 3회 이상 → 평균이 아니라 **분산까지 보고**
- **평가 구간**: 4.4절의 보수적 대리 기준(2026-04-24 이후)을 기본으로 하되, 그 이전 구간을 쓸 때는 마스킹 테스트 결과를 함께 싣는다

| 함정 | 내용 | 대응 |
|---|---|---|
| **학습 데이터 룩어헤드** | LLM이 과거 구간의 결과를 이미 알고 있음. 과거 백테스트 성적은 구조적으로 과대평가됨 | ① 컷오프 이후 구간만 평가 — 단 DeepSeek는 컷오프 미공시이므로 **4.4절의 대리 기준**을 쓴다 ② 종목명·날짜 마스킹 테스트 ③ **전진 기록을 주 평가로** |
| 과최적화 | 프롬프트 튜닝도 파라미터 튜닝이다 | 홀드아웃 구간 분리, 튜닝 횟수 기록 |
| 생존 편향 | 상폐·합병 종목 빠진 유니버스 | 시점 기준 구성종목 사용 |
| 뉴스 타임스탬프 | 벤더가 주는 발행 시각에 재발행·수정 시각이 섞인다. 장중 공개 시각이 부정확하면 미래 정보 유입 | `published_at`·`collected_at`을 둘 다 저장하고 어긋나면 `collected_at` 기준. 장마감 후 반영 |
| 프레임워크 자체 버그 | 데이터 접근 계층에서 미래 데이터 유입 사례 흔함 | 하네스 쪽에서 **독립 검증** |
| **모델 버전 드리프트** | 같은 별칭 뒤에서 모델이 갱신되면 전후 결과를 비교할 수 없다 | 4.3절 — 응답의 모델 버전·호출 시각 전량 로깅, 버전 경계에서 성적을 섞지 않음 |

> 룩어헤드 통제 여부에 따라 결과가 뒤집히므로, 비교 리포트에는 **통제 전/후 수치를 둘 다** 싣는다.

## 8. Phase B — 자체 아키텍처 (미국·한국 분기)

```
[데이터 레이어]  as-of 스냅샷 저장소 (전 항목 타임스탬프 보유)
   └ 공통 인터페이스 (get_prices / get_filings / get_news / get_macro)
        ├─ US 어댑터   : yfinance, SEC EDGAR(filing date), ALFRED(vintage), Finnhub(뉴스)
        └─ KR 어댑터   : pykrx·FinanceDataReader, DART(접수일자), ECOS, 네이버 검색 API(뉴스), 투자자별 수급
        ↓
[LLM 레이어]  얇은 추상화 (DeepSeek, 모델·모드 선택 + 버전·토큰·비용 로깅)
        ↓
[분석 에이전트]  병렬 · 시장별 프롬프트 분기
   펀더멘털 │ 기술적 │ 뉴스·센티먼트 │ 거시 │ 수급(KR 전용 비중 ↑)
        ↓  (구조화 JSON: 신호, 확신도, 근거, 반대근거, 참조 데이터)
[논쟁 레이어]  강세 리서처 ↔ 약세 리서처, N라운드 반박 → 쟁점 요약
        ↓
[리스크 매니저]  변동성 · 상관관계 · 섹터 편중 → 승인 / 기각 (거부권 보유)
        ↓
[의견 산출]  종목별 최종 의견 + 확신도 + 근거 기록
        ↓
[리플렉션]  5일·20일 뒤 결과 대조 → 메모리 적재
```

**시점 정합성 규칙 (데이터 레이어의 실제 난이도는 여기 있다)**

지표 목록을 아는 것은 어렵지 않다. 어려운 것은 "그 시점에 실제로 알 수 있었던 값"만 남기는 일이다.

| 규칙 | 내용 |
|---|---|
| **vintage 사용** | GDP·고용·산업생산·PMI는 사후 수정된다. FRED에서 그냥 받으면 최종 수정치가 오지만 당시 시장은 최초 발표치를 봤다. **ALFRED vintage 조회로 "그 날짜에 알려져 있던 값"을 쓴다.** 이게 불가능한 지표는 아예 쓰지 않는다 |
| **발표 시각 단위** | 날짜가 아니라 타임스탬프로 붙인다. CPI는 미 동부 08:30(장전), FOMC는 14:00(장중). 날짜 단위로 조인하면 FOMC 결과가 그날 아침 판단에 새어 들어간다 |
| **공시 제출일 기준** | 재무비율은 회계기간 종료일이 아니라 **제출일**에 사용 가능해진다. 3월 말 분기 실적은 5월에 나온다. EDGAR filing date / DART 접수일자를 기준으로 붙인다 |
| **뉴스 발행 시각** | 장중 공개분은 다음 판단 시점부터 사용. `published_at`과 `collected_at`을 **둘 다** 저장하고, 발행 시각이 없거나 수상하면 보수적으로 `collected_at`을 쓴다 |

**뉴스 소스 구성 (시장별 분리)**

영어권 벤더는 한국 기사를 제대로 다루지 못한다. 뉴스만은 시장별로 다른 소스를 쓰되 `get_news()` 인터페이스 뒤에 숨긴다.

| 용도 | 소스 | 한도 | 왜 |
|---|---|---|---|
| **US 메인** | Finnhub `company-news` | 분당 60콜 (무료·비상업) | 후보 중 한도가 압도적으로 넉넉하다. 종목 + 날짜 범위 쿼리 지원 |
| **KR 메인** | 네이버 검색 API (뉴스) | 애플리케이션당 일 2.5만 회 수준 | 무료 한도가 크고 `pubDate`를 준다 |
| KR 확장 (신청 대기) | 빅카인즈 | 데이터 제공 신청·승인 필요 | 매체가 정제돼 있고 과거 아카이브까지 열린다. 승인되면 KR 메인을 대체 |
| **센티먼트 베이스라인** | Alpha Vantage `NEWS_SENTIMENT` | 일 25회 | **수집용이 아니다.** 종목별 sentiment·relevance가 사전 계산돼 나오므로 LLM 센티먼트 에이전트와 겨룰 **제3자 룰 기반 기준선**으로 쓴다 (FinRL을 비LLM 베이스라인으로 둔 것과 같은 논리). 상위 후보 종목에만 호출 |

**한도가 왜 선택 기준인가.** 과거 뉴스 아카이브를 살 수 없어 매일 수집해 직접 쌓는 것이 전제다. 수집이 한도에 막히면 그날 구멍이 생기고 **그 구멍은 나중에 메울 수 없다.** 일 25회짜리를 메인에 두면 이 전제가 무너진다.

**관련성은 버리지 않고 등급으로 저장한다** (2026-09-15 실측 반영)

네이버는 본문까지 매칭하는 키워드 검색이고 스니펫에 검색어가 거의 항상 들어 있다.
그래서 "종목명이 언급됐는가"로는 거를 수 없다 — 실측상 100% 통과한다.
삼성전자 1,000건 중 **제목 매칭은 18%**, 나머지 82%는 요약에만 있는 스쳐 언급이었다.

| 등급 | 뜻 | 쓰임 |
|---|---|---|
| `title` | 제목에 종목명 | **기본 파이프라인이 에이전트에 넘기는 것** |
| `summary` | 요약에만 | 저장만. "스쳐 언급도 예측력이 있나"를 추가 호출 없이 사후 재채점 |
| `none` | 본문에만 매칭 | 저장만 |

별도로 `vendor_tagged`를 둔다. Finnhub는 티커로 태깅해 돌려주므로 제목 매칭 없이도 1차
자료지만 네이버는 보증이 없다. `is_primary = vendor_tagged or relevance == "title"`.

82%를 버리지 않는 이유는 에이전트 부분집합 ablation과 같다 — **한 번 받은 것으로 나중에
다른 질문에 답할 수 있게** 해 둔다. 버리면 그 질문을 영영 못 던진다.

**수집 주기는 종목별로 다르다** (2026-09-15 실측 반영)

`start` 상한이 1,000이라 한 번에 최대 1,000건인데, 그것이 덮는 구간은 언급 빈도에
반비례한다. 실측 편차가 27배였다.

| 종목 | 1,000건이 덮는 구간 | 배정 주기 |
|---|---|---|
| 삼성전자 | 7.0시간 | 3시간 |
| 한화에어로스페이스 | 192.5시간 (8일) | 24시간 |

하루 1회로 통일하면 삼성전자는 매일 17시간이 빈다. 벤더 제약이라 코드로 풀 수 없다.
기준은 **1,000건 한도의 절반(500건)으로 주기를 덮을 수 있는가** — 뉴스가 몰려도 버티는
여유다. 등급은 3/6/12/24시간, `config/universe.json`의 `collect_every_hours`에 둔다.

수집이 lookback 경계에 못 닿으면 **커버리지 미달로 기록**한다. 조용히 넘어가면
그만큼이 영구 손실인데 그 사실조차 모르게 된다.

**네이버 API의 실무 제약** (KR 어댑터의 실제 난이도는 여기 있다)

- **날짜 범위 파라미터가 없다.** `sort=date`로 받아 `pubDate`로 직접 자른다. 과거 구간 조회는 불가능하다
- 한 검색어당 최대 1,000건 (`display` 100 × `start` 1000)
- `pubDate`는 KST. 저장은 UTC로 통일한다
- `title`·`description`에 `<b>` 태그와 HTML 엔티티가 섞여 온다. 언이스케이프 없이 프롬프트에 넣지 않는다
- **종목코드 검색이 안 되고 회사명으로 쿼리해야 해 동명이의 잡음이 크다**("한화" → 야구단 기사). 매체 화이트리스트 + 종목명 재확인 필터가 사실상 필수
- 본문 크롤링은 하지 않는다. 제목·요약·링크·발행시각까지만 저장한다

발급 절차와 소스별 상세는 `docs/data-sources.md`.

**수집·저장 (2026-09-15 구현)**

| 대상 | 위치 |
|---|---|
| 기사·수집이력·gap | `data/mas_trade.sqlite3` |
| 벤더 원본 응답 | `data/snapshots/raw/` |

- **중복은 구조적으로 막는다.** `(symbol, content_hash)` PRIMARY KEY. 파일 기반이던 때는
  중복 검사 범위가 날짜별 파일이어서, 1시간 주기로 같은 기사를 하루 24번 다시 받다가
  자정을 넘길 때마다 중복이 새로 생겼다.
- **`INSERT OR IGNORE`다.** `collected_at`이 최초 관측 시각으로 고정되어야 `known_at`의
  보수적 판정이 유지된다. 나중 값으로 덮으면 "언제 알았나"가 뒤로 밀린다.
- **스케줄은 코드가 정한다.** cron은 한 시간마다 깨우기만 하고, 대상 선정은
  `collection_runs`의 마지막 수집 시각과 종목별 주기가 한다. cron에 흩어 놓으면 주기의
  근거(실측값)와 실행 설정이 갈라진다.
- **lookback은 마지막 수집 이후 경과 시간의 1.5배**다 (하한 1시간, 상한 7일).
  주기 기준 고정값은 평소엔 과하게 받아 페이지 상한에 가까워지고, 장기 중단 뒤에는
  그 구간을 못 메운다. 겹쳐 받는 비용은 0 — 중복은 DB가 막는다.
- **수집 실패와 커버리지 미달은 gap으로 남는다.** 실패한 수집은 이력에 기록하지 않는다 —
  기록하면 "방금 돌았다"로 판정되어 다음 주기까지 재시도하지 않는다.

**범위에서 제외하는 것**

- **Earnings Surprise (컨센서스 대비 실적).** 개념은 유효하지만 **과거 시점의 컨센서스 EPS는 I/B/E/S·FactSet 등 기관용 유료 데이터**이고 개인 접근이 사실상 불가능하다. 무료 소스가 주는 컨센서스는 현재 스냅샷뿐이라 과거로 되돌릴 수 없다. 국내도 마찬가지.
  → 대체: **실적 발표일 전후 주가 반응**을 관측 변수로 사용 (컨센서스를 직접 쓰지 않고 시장 반응으로 간접 측정)
- **매크로 지표 과다 투입.** 금리·달러·크레딧스프레드·유가는 상관이 매우 높아 전부 넣어도 정보량은 늘지 않고 과적합만 늘어난다. 축당 대표 지표 1~2개로 제한.

**매크로 에이전트의 구조적 한계 (우선순위 후순위)**

매크로 지표는 대부분 월간이다. 3개월 전진 검증이면 **관측 샘플이 3개**라 통계적으로 검증할 방법이 없다. 넣더라도 "검증된 구성요소"가 아니라 "맥락 제공자"로 취급하고, 기여도 측정 대상에서는 제외하거나 별도 취급한다.

**시장 분기 설계 규칙**

- 데이터 어댑터는 **공통 인터페이스 뒤에 숨긴다.** 상위 에이전트 코드는 시장을 몰라야 함.
- **프롬프트는 시장별로 따로 관리한다.** 미국장용을 번역만 해서 한국장에 쓰면 성능이 떨어진다. 공시 형식(10-K vs 사업보고서), 회계 표기, 뉴스 톤, 개인 수급 비중, 공매도 규제가 전부 다름. 모델의 한국어 처리 자체를 먼저 검증한다(4.6절).
- 공통 로직(논쟁 진행, 스키마 검증, 로깅)은 **한 벌만** 유지.
- 결과는 **절대 합산하지 않는다.** US 인스턴스와 KR 인스턴스는 끝까지 따로 보고.

**공통 설계 규칙**

- **계산은 코드, 해석은 LLM.** PER·변동성·상관계수·베타·샤프 등 모든 수치는 결정론적 파이썬 코드가 계산해 JSON으로 넘긴다. LLM이 직접 산술을 하게 두면 조용히 틀린 숫자가 섞이고, 그 숫자가 근거로 로그에 남아 사후 검증까지 오염시킨다. LLM의 일은 **주어진 수치를 해석·비교·판단**하는 것뿐이다.
- **리스크 매니저는 거부권을 가진다.** 경고만 하는 조언자가 아니라 승인/기각 게이트다. LLM이 제안하고 룰 엔진이 허가하는 비대칭 구조로 둔다. 기각 시 사유를 코드로 기록 (섹터 집중, 상관 과다, 변동성 레짐, 포지션 한도).
- 모든 에이전트 출력은 **스키마 강제**
- 프롬프트·응답·데이터 스냅샷 **전량 저장** + **모델 버전·토큰·비용**까지 (재현성의 전제, 4.3절)
- 상태 그래프 프레임워크(LangGraph 계열)로 단계 분리, 에이전트 교체 가능하게. **LLM 벤더도 같은 이유로 교체 가능하게**(4.7절)
- **비용 통제**: 저가 모델로 1차 스크리닝 → 상위 후보만 고성능 모델 (모델 매핑은 4.1절, 캐시·오프피크는 4.2절)

## 9. Phase C — 전진 검증 (모의투자 대신)

주문 체결 시뮬레이션(호가·잔고·부분체결)은 만들지 않는다. 대신 **실제 주가 등락으로 판단력을 직접 채점**한다. 평가는 두 층으로 나뉜다.

### 9.1 층 1 — 시그널 평가 (주 평가)

이게 본 평가다.

- **주 1회**, 정해진 요일·시각에 시스템이 유니버스 전 종목에 대해 의견을 낸다
  → `{종목, 방향(매수/보유/매도), 확신도 0~1, 근거, 반대근거, 기각 사유}`
- 그 시점 종가를 기준가로 박아두고, **5거래일 / 20거래일 뒤 실제 등락률**을 붙인다
- **의견 1건 = 샘플 1건.** 종목 15개 × 주 12회 = 180샘플 → 3개월에도 통계적으로 말할 게 생긴다
- 실행 시각은 **오프피크(KST 심야~새벽)** 에 고정한다(4.2절). 요일·시각을 고정해야 비교도 가능하다

측정 항목

| 항목 | 의미 |
|---|---|
| 방향 적중률 | 시장 상승률 대비 초과 여부로 판정 (그냥 올랐는지가 아니라) |
| **확신도-수익 상관** | 확신도 높다고 한 종목이 실제로 더 올랐나 ← 가장 중요한 지표 |
| 에이전트별 기여도 | 펀더멘털/기술적/센티먼트 각각의 의견만으로 채점했을 때 성적 |
| 논쟁 효과 | 논쟁 전 초안 의견 vs 논쟁 후 최종 의견 성적 차이 |
| **의견 분산도** | 에이전트 간 의견이 갈린 정도 자체를 하나의 피처로 기록. 전통 파이낸스에서 애널리스트 의견 분산이 큰 종목일수록 이후 수익률이 낮다는 연구(Diether·Malloy·Scherbina, 2002)가 있어 검증 가치가 있다. **로그에 이미 에이전트별 의견이 남으므로 열 하나 추가로 추가 비용 0** |
| 시장 간 격차 | 같은 구조가 US와 KR에서 얼마나 다른 성적을 내는가 |
| 결정당 비용 | 시그널 1건을 만드는 데 든 토큰·요금 (모델·모드별로 분해) |

**무료 ablation — 에이전트 수가 성능을 올리는가**

"에이전트 1개 vs 3개 vs 5개 vs 7개" 비교를 각각 따로 돌리면 LLM 호출이 몇 배로 뛰고, 백테스트로 하면 룩어헤드가 그대로 들어가 결론을 믿을 수 없다.

대신 **한 번 돌린 시그널 로그에서 에이전트 부분집합만으로 사후 재채점**한다. 에이전트별 개별 의견이 전부 저장되므로, 펀더멘털만 / 펀더멘털+뉴스 / 전체 등 임의 조합의 성적을 **추가 호출 없이** 계산할 수 있다. 비용 1배로 같은 질문에 답한다.

한계: 논쟁 레이어는 조합에 따라 결과가 달라지므로 사후 재구성이 불가능하다. 논쟁 효과만 별도 실행으로 측정한다.

### 9.2 층 2 — 가상 보유 포트폴리오 (보조 지표)

직관적인 "그래서 얼마?"를 보기 위한 보조 트랙.

- **종목당 동일 금액 가중.** 임의 수량(예: A 10주, B 3주)은 비중이 우연히 정해져서 실력과 운이 섞인다. 동일 금액이면 **종목 선택 자체만** 평가된다.
- 미국·한국 각각 독립 포트폴리오, **가상 원금 각 1,000만 원 상당**
- 주 1회 의견에 따라 비중 조정 (매수 → 편입, 매도 → 제외, 나머지 동일가중 재분배)
- **수익률은 현지통화 기준.** 원화 환산하면 환율 등락이 섞여 시스템 성적이 오염된다. 환 효과는 별도 열로만 기록.
- 배당은 재투자 가정, 거래비용은 6절 기준 적용

**비중 판단 트랙 (비교군)**

시스템에게 목표 비중까지 제시하게 하되, 그것을 기본 운용에 쓰지 않는다. **동일 금액 가중이 기준선, LLM 제시 비중이 비교군**으로 두 포트폴리오를 병행 추적한다.

이유: 비중까지 LLM에 맡기면 성적이 "종목을 잘 골랐나"인지 "비중을 잘 줬나"인지 분리되지 않는다. 3개월 표본으로 두 능력을 동시에 검증하는 것은 불가능하다. 두 트랙을 나눠 두면 나중에 **"비중 판단이 종목 선택 위에 가치를 더했는가"**를 독립적으로 답할 수 있다. 비중 결정은 기본 설정이 아니라 **검증 대상**이다.

### 9.3 왜 층 2만 보면 안 되나

3개월간 주 1회면 판단 시점이 12번뿐이다. 사실상 표본 12개라 어떤 결론도 낼 수 없고, 그 기간 시장이 올랐는지에 결과가 지배된다. **시그널 단위로 쪼개야 의미가 생긴다.**

### 9.4 벤치마크

| 시장 | 벤치마크 |
|---|---|
| US | S&P500 buy&hold, 동일가중 랜덤 15종목, **DeepSeek 단일 호출**(4.5절) |
| KR | KOSPI200 buy&hold, 동일가중 랜덤 15종목, **DeepSeek 단일 호출**, **코스콤 테스트베드 알고리즘 수익률 분포(중앙값·사분위)** |

두 시장을 합산한 숫자는 만들지 않는다.

### 9.5 리뷰 주기

4주마다: 에이전트별 기여도 재계산 → 가중치·역할 조정 → 조정 이력 기록(튜닝 횟수 관리). **모델 버전이 바뀐 이력도 같은 로그에 남긴다**(4.3절).
**최소 3개월 누적 전에는 성과를 해석하지 않는다.**

## 11. 산출물

1. **오픈소스 프레임워크 비교 리포트** — 동일 조건 비교는 공개 자료가 드물어 그 자체로 기술 글 소재
2. **시중 AI 트레이딩 도구 조사표** — 유형·AI 실체·공시 방식 정리
3. **재사용 가능한 백테스트 하네스** — 이후 모든 실험의 기반
4. **시그널 로그 데이터셋** — 종목 의견 + 확신도 + 근거 + 실제 등락 + 모델 버전·비용. 시간이 지날수록 가치가 커지는 유일한 자산. 단 **무료 티어 뉴스는 재배포가 금지**되므로, 공개를 전제로 기사 본문은 빼고 URL·발행시각·해시만 남기는 구조로 처음부터 만든다

## 12. 성공 기준

"벤치마크를 이겼다"가 아니라:

- 서로 다른 프레임워크를 **공정하게 비교할 수 있게 되었는가**
- 룩어헤드가 통제된 상태에서 **3개월 이상, 150건 이상의 시그널 기록**을 확보했는가
- **확신도가 실제 수익과 상관을 보이는가** (상관이 0이면 확신도는 장식)
- 각 에이전트의 **기여도를 정량화**했는가
- 멀티에이전트 구조가 **같은 모델의 단일 호출을 유의미하게 이기는가** (못 이기면 구조를 단순화하는 게 정답)
- 같은 구조가 **미국장과 한국장에서 어떻게 다르게 작동하는지** 설명할 수 있는가
- **에이전트를 늘린 것이 실제로 성적을 올렸는가** (사후 재채점으로 확인)
- **LLM의 비중 판단이 동일가중 대비 가치를 더했는가**
- **시그널 1건당 비용을 알고 있는가** (모르면 확장 가능성을 말할 수 없다)
