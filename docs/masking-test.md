# 마스킹 테스트 계획 — 계측기를 먼저 교정한다

## 측정 대상을 먼저 못박는다

**이 프로젝트가 재려는 것은 LLM의 능력이 아니다.**

> **프롬프트와 멀티에이전트 구조로 구현한 로보어드바이저의 정확도.**

LLM은 부품이다. 같은 모델에 다른 프롬프트·다른 구조를 얹으면 다른 성적이 나오고,
우리가 만드는 것은 그 **구조**다. 기획서 12절이 "멀티에이전트 구조가 같은 모델의
단일 호출을 이기는가"를 성공 기준으로 둔 이유가 이것이다 — 모델을 고정하고
**구조만 변수로** 둔다(4.5절).

이 구분이 마스킹 테스트의 성격을 정한다.

## 그래서 마스킹 테스트는 성능 측정이 아니라 계측기 교정이다

시스템 정확도를 **과거 데이터로** 주장하려면 백테스트라는 자가 믿을 만해야 한다.
그런데 부품인 LLM이 과거 구간의 결과를 기억하고 있으면 그 눈금이 휜다.

> **재려는 것**: 우리 시스템이 과거를 판단할 때, 주어진 지표를 해석하는가
> 아니면 모델의 기억이 새어 들어오는가.

기획서 7절이 요구한 "종목명·날짜 마스킹 테스트"의 구현 계획이다.

**한 번 재고 끝나지 않는다.** 룩어헤드 크기는 **구성(프롬프트 + 구조)마다 다르다.**
지금 있는 것은 단일 호출 베이스라인뿐이므로 이번 측정은 베이스라인의 눈금이다.
분석 에이전트·논쟁 레이어가 붙으면 **그 구성으로 다시 잰다.** 구성이 바뀔 때마다
붙는 교정 절차로 둔다.

---

## 0. 왜 지금 이것부터인가

과거 백테스트를 돌리고 싶은 유혹이 있다 — 3개월을 기다리는 대신 1년치 결과를 몇 시간에
얻을 수 있어 보인다. **비용도 시간도 걸림돌이 아니다.**

```
1년 × 주 1회 × 30종목 = 1,560회   오프피크 $12.95   8병렬 2.4시간
```

그런데 그 숫자를 **해석할 근거가 없다.** 기획서 7절·4.4절과 `CLAUDE.md` 4절이 같은
말을 한다 — LLM은 과거 구간 결과를 이미 알고 있어 과거 백테스트는 구조적으로
과대평가된다. DeepSeek는 학습 컷오프를 공시하지 않아 "컷오프 이후만 평가"라는 표준
처방도 문자 그대로 적용할 수 없다.

**마스킹 테스트는 그 해석 근거를 만드는 실험이다.** 이걸 먼저 하지 않으면 뒤따르는
어떤 백테스트 숫자도 읽을 수 없다.

### 0.1 "정확도"를 조작적으로 정의한다

로보어드바이저의 정확도라는 말은 그대로 쓰면 애매하다. 무엇을 재는지 셋으로 나눈다.

| 층 | 지표 | 왜 |
|---|---|---|
| **층 1 (주 평가)** | 지수 대비 초과수익 **방향 적중률** | 기획서 9.1·9.3 — 시그널 단위라야 3개월에 표본이 생긴다 |
| **층 1 (최우선)** | **확신도-수익 상관** | 9.1절이 가장 중요한 지표로 꼽았다. 확신도가 장식이면 로보어드바이저로 못 쓴다 |
| 층 2 (보조) | 위험조정수익 (샤프·MDD) | "그래서 얼마?"에 답한다. 판단 시점이 적어 단독으로는 못 읽는다 |

**"벤치마크를 이겼다"는 성공 기준이 아니다**(기획서 12절). 정확도는 이겼는지가 아니라
**판단이 실제 등락과 얼마나 맞물리는지**로 정의한다.

### 0.2 동종 집단 — 로보어드바이저를 만든다면 비교 대상도 그것이다

기획서 9.4절이 이미 지목해뒀다. **코스콤 로보어드바이저 테스트베드**는 43개 금융사의
알고리즘 수백 개에 대해 동일 조건 수익률을 공시한다.

**단일 알고리즘이 아니라 분포 전체를 벤치마크로 쓴다**(3.3절 — 업체가 홍보하는
최상위 하나는 체리피킹이다). 우리 성적이 그 분포의 몇 분위인지가 "로보어드바이저로서
쓸 만한가"에 대한 가장 직접적인 답이다.

이번 범위 밖이지만, **측정 대상을 시스템으로 정한 이상 이게 최종 비교군**이라는 것을
여기 적어둔다.

### 0.3 이 실험이 답하지 않는 것

| | |
|---|---|
| 실전 기대수익 | 답하지 않는다. 그건 전진 검증(Phase C)의 몫이다 |
| 뉴스의 기여도 | **답할 수 없다.** 과거 구간에 뉴스가 0건이다(아래 1.2) |
| 룰 대비 우위 | 이번 범위 밖. 룰 비교군은 `docs/baselines.md`에 이미 있다 |

## 1. 제약 — 먼저 인정하고 시작한다

### 1.1 학습 데이터 룩어헤드 (재려는 대상)

DeepSeek V4 프리뷰 공개일 **2026-04-24**를 보수적 대리 기준으로 쓴다(기획서 4.4절).
1년 구간(2025-09 ~ 2026-09)은 **그 경계를 가로지른다.** 의도한 것이다 —
경계 전후로 마스킹 효과가 갈리면 그 자체가 룩어헤드의 증거다.

### 1.2 과거 구간에는 뉴스가 없다 (고칠 수 없다)

```
뉴스 known_at   2026-09-13 ~ (수집 시작 시점)
1년 전 이전 뉴스        0건
대리기준(04-24) 이전    0건
```

따라서 이 실험은 **가격 지표만 보는 에이전트**를 대상으로 한다. 전진 검증 중인
시스템(뉴스 포함)과 **다른 시스템이다.** 성적을 전이시키지 않는다.

역설적으로 이게 마스킹을 깨끗하게 만든다 — 가릴 뉴스 본문이 없다.

### 1.3 시스템 수준 룩어헤드는 마스킹으로 안 풀린다

**측정 대상이 시스템이면 룩어헤드도 시스템 전체에서 봐야 한다.** LLM 학습 룩어헤드만
보면 놓치는 것이 있다.

| 출처 | 상태 |
|---|---|
| 데이터 접근 | as-of 인터페이스로 막았다 (`architecture.md` 4절, 방어선 6군데) |
| LLM 학습 데이터 | **이 실험이 재려는 것** |
| **유니버스 선택** | **막지 못했다.** 15종목을 2026년에 골라 2024년 백테스트에 쓴다 |

세 번째가 이번 실험으로 풀리지 않는다. 마스킹을 해도 **"2026년까지 살아남아 시총
상위에 있는 15종목"이라는 사실 자체가 과거 구간에 대한 정보**다. 상폐·부진 종목이
애초에 유니버스에 없다.

이것은 기획서 7절의 "생존 편향 — 시점 기준 구성종목 사용"이고, 14.1절에 선행 조건으로
적어둔 문제다. **마스킹 결과를 읽을 때 이 편향이 별도로 남아 있음을 함께 적는다.**

### 1.4 가격 수준 자체가 종목을 드러낸다

`삼성전자 256,000원`은 이름을 가려도 종목을 특정한다. **절대 가격을 넘기지 않고
지표(비율)만 넘긴다.** 다행히 `src/compute/indicators.py`의 출력은 이미 전부 비율이고,
`reference.close`만 예외다.

### 1.5 완전한 마스킹은 불가능하다

지표 패턴 자체가 시점을 암시할 수 있다(예: 특정 월의 -30% 구간). 마스킹은
**룩어헤드를 없애는 장치가 아니라 그 크기를 재는 장치다.** 이 한계를 결과에 명시한다.

## 2. 설계

### 2.1 무엇을 가리고 무엇을 남기나

| 항목 | 마스킹 | 이유 |
|---|---|---|
| 종목명 · 티커 | **가린다** → `종목 A` | 기억을 부르는 1차 열쇠 |
| `as_of` · 기준일 | **가린다** → `T`, `T-1` 상대 표기 | 시점 특정을 막는다 |
| 절대 가격 | **가린다** → 100으로 정규화 | 가격 수준이 종목을 드러낸다(1.4) |
| 시장 (KR/US) | 남긴다 | 프롬프트가 시장별이라 필요. 시점 특정에 기여하지 않는다 |
| 섹터 | 남긴다 | **도메인 지식과 기억을 구분하기 위해서다.** "반도체는 사이클이 있다"는 정당한 지식이고, "2024년 3월 삼성전자"는 기억이다 |
| 지표 전부 | 남긴다 | 판단의 실제 재료 |

두 버전은 **프리픽스를 공유하지 않는다** — 마스킹 버전은 별도 시스템 프롬프트를 쓰고
`prompt_version`으로 구분된다.

### 2.2 쌍대 비교

같은 구간·같은 종목·같은 지표를 **두 번** 돌린다. 시장 변동이 상쇄되므로 독립 표본보다
검정력이 높다. 같은 시점의 두 판단을 직접 짝지어 비교한다.

### 2.3 규모

```
구간   2025-09 ~ 2026-09 · 주 1회(수요일 07:00 KST) · 52회차
호출   52 × 30종목 × 2버전 = 3,120회
비용   오프피크 약 $26
시간   8병렬 약 4.8시간
```

### 2.4 판정 기준

시장별 채점 대상 약 429건(hold 약 45% 제외) 기준.

| 지표 | 2σ 기준 | 해석 |
|---|---|---|
| 적중률 차이 | **6.8%p** | 이보다 크면 이름·날짜에서 정보를 얻고 있었다 |
| 확신도-수익 상관 차이 | 표본 확정 후 산출 | 확신도가 기억에 기대는가 |

**호라이즌별로 따로 본다.** 5거래일은 주 1회와 맞닿아 겹침이 없어 독립 구간 50개지만,
20거래일은 4배 겹쳐 유효 표본이 1/4이다. 두 숫자를 같은 표에 나란히 놓지 않는다.

**구간 분해가 핵심이다.** 대리기준(2026-04-24) 전후로 나눠 본다.

| 관찰 | 뜻 |
|---|---|
| 경계 **이전** 구간에서만 마스킹 효과가 크다 | **전형적인 학습 룩어헤드.** 그 구간 성적을 폐기한다 |
| 경계 전후 모두 효과가 작다 | 지표만으로 판단하고 있다. 백테스트 숫자를 (조심스럽게) 읽을 수 있다 |
| 경계 **이후**에도 효과가 크다 | 마스킹이 룩어헤드가 아닌 다른 것을 깨뜨리고 있다. 설계를 의심한다 |

## 3. 결과를 어디에 쓰는가

### 3.1 백테스트 숫자는 전진 검증과만 맞대어 본다

**백테스트 성적을 단독으로 보고하지 않는다.** 쓰임은 하나다 — 전진 검증에서 나온
실제 성적을 해석할 때 옆에 놓는 참조점이다.

```
전진 성적이 백테스트보다 크게 나쁘다   -> 백테스트가 룩어헤드로 부풀었다 (마스킹 차이가 뒷받침하면 확정)
전진 성적이 백테스트와 비슷하다        -> 그 구간 백테스트를 참고로 쓸 수 있다
```

### 3.2 개선 대상 — 이미 증거가 있는 것부터

| 대상 | 현재 증거 |
|---|---|
| **확신도 폭** | 두 번의 실행에서 모두 sd 0.070, 범위 0.40~0.62. 우연이 아니라 성향으로 보인다. 순위상관 검정력이 약해진다 |
| **hold 비율** | 43~53%. 적중 판정에서 빠져 실효 표본이 절반이 된다 |
| 프롬프트 문구 | 마스킹 버전에서 무엇이 무너지는지가 단서를 준다 |
| 지표 구성 | 어떤 지표가 실제로 근거에 인용되는지 `key_evidence`로 집계 가능하다 |

### 3.3 튜닝 규율 — 이게 가장 중요하다

기획서 7절: **"프롬프트 튜닝도 파라미터 튜닝이다. 홀드아웃 구간 분리, 튜닝 횟수 기록."**

| 규칙 | 근거 |
|---|---|
| **전진 검증이 홀드아웃이다** | 백테스트는 튜닝장, 전진은 검증장. 전진 구간은 정의상 모델도 우리도 못 본 데이터다 |
| **전진 반영은 분기 1회로 제한** | 전진 표본이 3개월에 시장당 약 98건뿐이다. 자주 바꾸면 표본을 태운다 |
| **프롬프트 버전 경계에서 성적을 섞지 않는다** | `runs.prompt_version`에 이미 기록된다. 경계 전후를 한 표에 넣지 않는다 |
| **튜닝 횟수를 센다** | 시도 횟수 자체가 과적합의 크기다. 일지에 남긴다 |

---

## 4. 하지 않는 것

- **백테스트 성적을 실전 기대수익으로 서술하지 않는다** (`CLAUDE.md` 4절)
- 마스킹 결과가 나오기 전에 백테스트 숫자를 보고하지 않는다
- 이번 범위에서 룰 비교군·층 2 포트폴리오를 돌리지 않는다 — 다중검정을 키운다
- **뉴스를 소급 생성하지 않는다.** 과거 뉴스는 살 수 없고 대체물을 만들면 그 자체가 오염이다

## 5. 산출물

1. 마스킹 / 비마스킹 시그널 전량 (기존 `signals`·`opinions`·`llm_calls` 스키마 그대로)
2. 구간 분해 비교표 — 대리기준 전후 × 호라이즌 × 시장
3. **룩어헤드 크기 추정치** — 이후 모든 백테스트 해석의 근거.
   **베이스라인 구성에 대한 값이다.** 구조가 바뀌면 다시 잰다
4. 개선 후보 목록과 그 근거
5. 일지 기록 — 튜닝 횟수 관리의 시작점

## 6. 착수 전 확인할 것

- `prompt_version`이 마스킹 버전을 구분하는가 (이미 해시 기반이라 자동)
- 3,120회를 병렬로 돌릴 때 DeepSeek 분당 한도에 걸리는가 — **미확인**
- `SignalStore`에 실험용 `kind`를 둘 것인가 (`baseline` / `masked`) — 전진 기록과
  섞이면 안 된다. **구성이 늘어나면 `kind`가 구성 식별자 역할을 한다**
  (`baseline` / `masked` / `agents` / `agents_masked` …)
