# 2026-09-16

정기 수집을 cron이 아니라 launchd로 걸고, 저장소를 `~/Desktop` 밖으로 옮겼다.
"노트북에서 돌린다"는 전제가 스케줄러 선택을 바꾼다는 걸 늦게 알아챘다.

## 결정

### 정기 실행은 cron이 아니라 launchd로 한다

`docs/HANDOFF.md`가 `5 * * * *` crontab을 1순위로 지정했는데, **노트북에서는 틀린
선택이다.** 이 저장소가 도는 기기는 MacBook Air다.

`pmset -g custom` (2026-09-16 확인)

```
배터리:  sleep 1    ← 1분 유휴면 잠든다
AC:     sleep 0    ← 안 잠든다
powernap 1
```

- **cron은 잠든 사이의 실행을 건너뛰고, 깨어나도 따라잡지 않는다.** 14:00에 자고
  있었으면 그 시각 수집은 영영 실행되지 않는다.
- **launchd의 `StartCalendarInterval`은 깨어날 때 한 번 실행한다.** `man launchd.plist`:
  "Unlike cron which skips job invocations when the computer is asleep, launchd will
  start the job the next time the computer wakes up. If multiple intervals transpire
  before the computer is woken, those events will be coalesced into one event."

뉴스는 거른 시간을 나중에 살 수 없다. 피크 200건/h에 한 번에 1,000건 한도이므로
**장중 5시간 이상 중단은 영구 손실**이다. 따라잡기 여부가 곧 데이터 손실 여부다.

#### 기각한 선택지

| 선택지 | 기각 사유 |
|---|---|
| **cron + `/usr/sbin/cron`에 전체 디스크 접근 권한** | 잠자기 문제가 그대로 남는다. TCC만 푸는 것이고 따라잡기는 여전히 없다. 게다가 cron에 디스크 전체를 여는 대가가 크다 |
| **Claude 예약 (`/schedule` 클라우드 routine)** | 클라우드에서 돈다. `data/mas_trade.sqlite3`와 `.env`가 gitignore라 그쪽에 없다. 수집해도 남의 샌드박스에 쌓이고 사라진다 |
| **Claude 세션 내 예약 (`CronCreate` / `/loop`)** | 세션에 묶여 있다. 터미널을 닫으면 죽는다 |
| **Claude에게 매시 수집을 시킴** | 비용이 0 대 N. 1h 주기 종목이 3개라 하루 24회다. 게다가 `collect_news.py`는 주기 판정·lookback·gap 기록을 이미 스스로 한다 — **판단할 것이 남아 있지 않다.** 실패 처리는 "기록하지 않아서 다음 주기에 재시도"라는 결정론적 경로인데, 여기에 LLM을 끼우면 되돌릴 수 없는 데이터를 다루는 자리에 비결정성이 들어간다. `CLAUDE.md`의 "계산은 코드, 해석은 LLM"에 정면으로 어긋난다 |

Claude 예약이 **맞는** 자리는 따로 있다. cron/launchd의 약점은 조용히 죽는 것이고,
로그를 읽어 "며칠째 수집이 0건이다"를 판정하는 건 해석 작업이다. 하루 1회 감시자로는
값을 더한다. 수집기로는 아니다. → 미결 항목으로 남긴다.

### 래퍼 이름은 `run_collect.sh`

핸드오프는 `scripts/cron_collect.sh`를 지정했지만 cron을 안 쓰므로 이름이 거짓이 된다.
`scripts/run_collect.sh`로 바꿨다.

### 래퍼가 스냅샷을 자동으로 지우지 않는다

`SNAPSHOT_RETENTION_DAYS`가 설정됐을 때만 지운다. 기본은 미설정 = 안 지움.
`CLAUDE.md`의 "파괴적 스크립트는 dry-run이 기본"을 따랐다. 지금 스냅샷은 5.5MB라
급하지 않다.

## 문제와 원인

### TCC는 launchd LaunchAgent도 막는다 — 정정

**어제·오늘 오전의 판단이 틀렸다.** "LaunchAgent는 사용자 권한으로 돌아서
`/usr/sbin/cron`보다 TCC 취급이 유리할 수 있다"고 적었는데, 실측으로 반증됐다.

`~/Desktop/2026 개인프로젝트/MAS_TRADE`에 둔 채 등록하고 실행한 결과 (2026-09-16 확인)

```
launchctl print → last exit code = 126
logs/launchd.err.log:
  shell-init: error retrieving current directory: getcwd: cannot access
  parent directories: Operation not permitted
  /bin/bash: .../MAS_TRADE/scripts/run_collect.sh: Operation not permitted
```

사용자 권한이든 아니든 **Desktop 아래면 막힌다.** 이사는 선택이 아니라 필수였다.

얻은 것도 있다. `runs = 1`이 찍혔으니 **launchd 트리거 자체는 정상**이고, 막히는 건
실행 순간의 파일 접근뿐이라는 게 분리 확인됐다.

### DART 스모크 테스트가 밤에 거짓 실패한다

`scripts/smoke_test_apis.py`의 DART 호출은 날짜 파라미터 없이 `list.json`을 부른다.
DART는 기본값이 당일이라, 공시가 아직 없는 새벽에는 `status=013 조회된 데이타가 없습니다`가
온다. 스크립트는 `status == "000"`만 통과로 보므로 **FAIL로 찍힌다.**

키 문제가 아니다. 같은 키로 `bgn_de=20260910 / end_de=20260915`를 조회하면
`status=000`, `total_count=2427` (2026-09-16 01:2x KST 확인).

핸드오프가 이사 검증용으로 "8개 중 7개 통과가 정상"이라고 지정한 스크립트라,
**이사 직후 새벽에 돌리면 이사가 뭔가 깨뜨린 것처럼 보인다.** 실제로 그렇게 보였고
확인하는 데 시간을 썼다. 아직 안 고쳤다 → 미결.

### 디스크가 87~90%

`/System/Volumes/Data` 228GB 중 여유 27GB (2026-09-16 확인, 측정 시점에 따라 21~28GB로
흔들린다 — macOS가 purgeable 공간을 정리한다). Time Machine 로컬 스냅샷은 없어서
지워서 확보할 여지가 없다.

이 프로젝트 탓은 아니다. 실측한 증가 속도 (2026-09-16)

| 항목 | 실측 |
|---|---|
| 기사 1건당 DB | 896 B (5,328,896 B ÷ 5,944건) |
| 수집 1회당 원본 스냅샷 | 중앙값 58 KB (최소 0 · 최대 354 KB) |
| 하루 수집 횟수 | 약 125회 (KR 110 + US 15, 종목별 주기 합산) |
| 합계 | **약 10 MB/일 = 300 MB/월 = 3.5 GB/년** |

27GB 여유에 연 3.5GB면 몇 년은 간다. 문제는 **디스크가 차면 SQLite 쓰기가 실패하고,
그 시간 뉴스는 영구 손실**이라는 점이다. 이 프로젝트가 감당 못 하는 실패 모드가
디스크에서 터진다. 래퍼에 여유 체크를 넣었다(10GB 미만 WARN, 1GB 미만 ABORT).

### CPU·발열·SSD 수명은 문제가 아니다

확인만 하고 넘어간다. 네트워크 대기가 대부분이고 SQLite `INSERT`는 순간이다. 30종목
강제 수집에서 체감 부하가 없었다. 연 3.5GB 쓰기는 SSD 내구성(수백 TB) 대비 무시 가능.
**Air에서 걱정할 것은 발열이 아니라 잠자기다.**

## 해결

### 저장소 이사

`~/Desktop/2026 개인프로젝트/MAS_TRADE` → `~/projects/MAS_TRADE`

같은 APFS 볼륨(`/dev/disk3s5`)이라 `mv`가 복사가 아니라 rename이다. 즉시 끝났고
데이터가 오가지 않았다. 확인: DB 5,328,896 B 동일, `.env` 있음, 스냅샷 70개, git 정상.

venv는 재생성했다(`rm -rf .venv` → `python3 -m venv` → `pip install -r requirements.txt`).
테스트 67건 통과.

### 새 파일

- `scripts/run_collect.sh` — 실행 래퍼. `${BASH_SOURCE[0]}`로 저장소 루트를 찾으므로
  **또 옮겨도 안 깨진다.** 타임스탬프 로깅, 10MB 로그 회전(3세대), 디스크 여유 체크,
  `mkdir` 원자적 락(30분 stale 해제), venv·`.env` 존재 확인, 실패 시 TCC 힌트 출력.
- `scripts/install_scheduler.sh` — 현재 경로로 plist를 생성해 `launchctl bootstrap`.
  **이사 후 인자 없이 다시 돌리면 그대로 재등록된다.** `--status` / `--run-now` / `--uninstall`.

plist는 `~/Library/LaunchAgents/com.ys.mastrade.collect.plist` (저장소 밖, git 무관).
`RunAtLoad`도 켰다 — 로그인·재부팅 직후 한 번 더 돈다. 어떤 종목을 실제로 돌릴지는
`collect_news.py`가 마지막 수집 시각으로 정하므로 중복 수집이 되지 않는다.

1. **실제 수집 쓰기 확인.** 위 검증은 대상 0건 실행이었다. `2026-09-16 02:05 KST`

   24시간 수집하는 건 구조적 한계다. 상시 전원 기기(라즈베리파이·소형 VPS)로 옮기는 게

3. **DART 스모크 테스트 거짓 실패** — `013`을 통과로 보거나 과거 날짜를 조회하도록

4. **디스크 정리** — 여유 27GB / 87%. ys가 직접 판단할 몫.
5. **감시자 자동화** — 하루 1회 로그·gap을 읽어 이상을 알리는 층. cron/launchd가 조용히
