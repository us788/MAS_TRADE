# 2026-09-16

정기 수집을 cron이 아니라 launchd로 걸고, 저장소를 `~/Desktop` 밖으로 옮겼다.
"노트북에서 돌린다"는 전제가 스케줄러 선택을 바꾼다는 걸 늦게 알아챘다.

## 결정

### 정기 실행은 cron이 아니라 launchd로 한다

`docs/HANDOFF.md`가 `5 * * * *` crontab을 1순위로 지정했는데, **노트북에서는 틀린
선택이다.** 이 저장소가 도는 기기는 MacBook Air다.

`pmset -g custom` (2026-09-16 확인)

```
배터리:  sleep 1    ← 1분 유휴면 잠든다
AC:     sleep 0    ← 안 잠든다
powernap 1
```

- **cron은 잠든 사이의 실행을 건너뛰고, 깨어나도 따라잡지 않는다.** 14:00에 자고
  있었으면 그 시각 수집은 영영 실행되지 않는다.
- **launchd의 `StartCalendarInterval`은 깨어날 때 한 번 실행한다.** `man launchd.plist`:
  "Unlike cron which skips job invocations when the computer is asleep, launchd will
  start the job the next time the computer wakes up. If multiple intervals transpire
  before the computer is woken, those events will be coalesced into one event."

뉴스는 거른 시간을 나중에 살 수 없다. 피크 200건/h에 한 번에 1,000건 한도이므로
**장중 5시간 이상 중단은 영구 손실**이다. 따라잡기 여부가 곧 데이터 손실 여부다.

#### 기각한 선택지

| 선택지 | 기각 사유 |
|---|---|
| **cron + `/usr/sbin/cron`에 전체 디스크 접근 권한** | 잠자기 문제가 그대로 남는다. TCC만 푸는 것이고 따라잡기는 여전히 없다. 게다가 cron에 디스크 전체를 여는 대가가 크다 |
| **Claude 예약 (`/schedule` 클라우드 routine)** | 클라우드에서 돈다. `data/mas_trade.sqlite3`와 `.env`가 gitignore라 그쪽에 없다. 수집해도 남의 샌드박스에 쌓이고 사라진다 |
| **Claude 세션 내 예약 (`CronCreate` / `/loop`)** | 세션에 묶여 있다. 터미널을 닫으면 죽는다 |
| **Claude에게 매시 수집을 시킴** | 비용이 0 대 N. 1h 주기 종목이 3개라 하루 24회다. 게다가 `collect_news.py`는 주기 판정·lookback·gap 기록을 이미 스스로 한다 — **판단할 것이 남아 있지 않다.** 실패 처리는 "기록하지 않아서 다음 주기에 재시도"라는 결정론적 경로인데, 여기에 LLM을 끼우면 되돌릴 수 없는 데이터를 다루는 자리에 비결정성이 들어간다. `CLAUDE.md`의 "계산은 코드, 해석은 LLM"에 정면으로 어긋난다 |

Claude 예약이 **맞는** 자리는 따로 있다. cron/launchd의 약점은 조용히 죽는 것이고,
로그를 읽어 "며칠째 수집이 0건이다"를 판정하는 건 해석 작업이다. 하루 1회 감시자로는
값을 더한다. 수집기로는 아니다. → 미결 항목으로 남긴다.

### 래퍼 이름은 `run_collect.sh`

핸드오프는 `scripts/cron_collect.sh`를 지정했지만 cron을 안 쓰므로 이름이 거짓이 된다.
`scripts/run_collect.sh`로 바꿨다.

### 래퍼가 스냅샷을 자동으로 지우지 않는다

`SNAPSHOT_RETENTION_DAYS`가 설정됐을 때만 지운다. 기본은 미설정 = 안 지움.
`CLAUDE.md`의 "파괴적 스크립트는 dry-run이 기본"을 따랐다. 지금 스냅샷은 5.5MB라
급하지 않다.

## 문제와 원인

### TCC는 launchd LaunchAgent도 막는다 — 정정

**어제·오늘 오전의 판단이 틀렸다.** "LaunchAgent는 사용자 권한으로 돌아서
`/usr/sbin/cron`보다 TCC 취급이 유리할 수 있다"고 적었는데, 실측으로 반증됐다.

`~/Desktop/2026 개인프로젝트/MAS_TRADE`에 둔 채 등록하고 실행한 결과 (2026-09-16 확인)

```
launchctl print → last exit code = 126
logs/launchd.err.log:
  shell-init: error retrieving current directory: getcwd: cannot access
  parent directories: Operation not permitted
  /bin/bash: .../MAS_TRADE/scripts/run_collect.sh: Operation not permitted
```

사용자 권한이든 아니든 **Desktop 아래면 막힌다.** 이사는 선택이 아니라 필수였다.

얻은 것도 있다. `runs = 1`이 찍혔으니 **launchd 트리거 자체는 정상**이고, 막히는 건
실행 순간의 파일 접근뿐이라는 게 분리 확인됐다.

### DART 스모크 테스트가 밤에 거짓 실패한다

`scripts/smoke_test_apis.py`의 DART 호출은 날짜 파라미터 없이 `list.json`을 부른다.
DART는 기본값이 당일이라, 공시가 아직 없는 새벽에는 `status=013 조회된 데이타가 없습니다`가
온다. 스크립트는 `status == "000"`만 통과로 보므로 **FAIL로 찍힌다.**

키 문제가 아니다. 같은 키로 `bgn_de=20260910 / end_de=20260915`를 조회하면
`status=000`, `total_count=2427` (2026-09-16 01:2x KST 확인).

핸드오프가 이사 검증용으로 "8개 중 7개 통과가 정상"이라고 지정한 스크립트라,
**이사 직후 새벽에 돌리면 이사가 뭔가 깨뜨린 것처럼 보인다.** 실제로 그렇게 보였고
확인하는 데 시간을 썼다. 아직 안 고쳤다 → 미결.

### 디스크가 87~90%

`/System/Volumes/Data` 228GB 중 여유 27GB (2026-09-16 확인, 측정 시점에 따라 21~28GB로
흔들린다 — macOS가 purgeable 공간을 정리한다). Time Machine 로컬 스냅샷은 없어서
지워서 확보할 여지가 없다.

이 프로젝트 탓은 아니다. 실측한 증가 속도 (2026-09-16)

| 항목 | 실측 |
|---|---|
| 기사 1건당 DB | 896 B (5,328,896 B ÷ 5,944건) |
| 수집 1회당 원본 스냅샷 | 중앙값 58 KB (최소 0 · 최대 354 KB) |
| 하루 수집 횟수 | 약 125회 (KR 110 + US 15, 종목별 주기 합산) |
| 합계 | **약 10 MB/일 = 300 MB/월 = 3.5 GB/년** |

27GB 여유에 연 3.5GB면 몇 년은 간다. 문제는 **디스크가 차면 SQLite 쓰기가 실패하고,
그 시간 뉴스는 영구 손실**이라는 점이다. 이 프로젝트가 감당 못 하는 실패 모드가
디스크에서 터진다. 래퍼에 여유 체크를 넣었다(10GB 미만 WARN, 1GB 미만 ABORT).

### CPU·발열·SSD 수명은 문제가 아니다

확인만 하고 넘어간다. 네트워크 대기가 대부분이고 SQLite `INSERT`는 순간이다. 30종목
강제 수집에서 체감 부하가 없었다. 연 3.5GB 쓰기는 SSD 내구성(수백 TB) 대비 무시 가능.
**Air에서 걱정할 것은 발열이 아니라 잠자기다.**

## 백테스트 하네스 설계 — `docs/harness.md`

수집이 자동화됐으니 다음은 기획서가 1순위 산출물로 꼽은 저울이다. 구현 전에

### 검토 중 나온 것 — 실행 시각이 기준가를 바꾼다

기획서 4.2절은 비용 때문에 시그널 생성을 "KST 심야~새벽"에 돌리라고 한다.
그런데 미국 정규장 마감(16:00 ET)이 한국 시각으로 **익일 05:00(EDT) / 06:00(EST)**다.
`zoneinfo`로 확인했다 (2026-09-16).

```
KST 07-16 02:00  =  ET 07-15 13:00 EDT  ->  마지막 마감 세션 2026-07-14   (D-2)
KST 07-16 07:00  =  ET 07-15 18:00 EDT  ->  마지막 마감 세션 2026-07-15   (D-1)
KST 01-16 02:00  =  ET 01-15 12:00 EST  ->  마지막 마감 세션 2026-01-14   (D-2)
KST 01-16 07:00  =  ET 01-15 17:00 EST  ->  마지막 마감 세션 2026-01-15   (D-1)
```

**KST 02:00에 돌리면 KR 기준가는 D-1 종가, US는 D-2 종가가 된다.** 서머타임 양쪽 다
같다. 기획서 12절 성공 기준이 "같은 구조가 US와 KR에서 어떻게 다르게 작동하는가"인데,
이대로면 구조 차이가 아니라 **기준가 시차를 보게 된다.**

제안은 실행 시각을 **KST 07:00~08:00**로 옮기는 것. 아직 확정 아님 — DeepSeek
오프피크 구간과 겹치는지 확인이 필요하다. 문서에는 벗어날 경우 **정합성을 택한다**고
적었다. 비용은 프리픽스 캐싱으로 줄일 여지가 있지만 어긋난 기준가는 나중에 못 고친다.

기각한 대안: 시장별로 실행 시각을 나누는 것 — 9.1절이 요일·시각 고정을 요구하므로
비교 가능성이 깨진다.

### 확정한 설계 결정

| 결정 | 이유 |
|---|---|
| `as_of`와 `forward`를 **모듈로 분리** | 에이전트에는 as_of만 노출한다. 같은 객체에 두면 실수로 미래를 본다 |
| 휴장일 캘린더를 만들지 않는다 | "5거래일"을 달력이 아니라 시계열 인덱스 오프셋으로 센다. 임시공휴일·조기폐장 관리는 영구 부채다 |
| `close_raw` / `close_adj` 둘 다 저장 | 기준가는 실제 거래가, 수익률은 수정가. 하나만 두면 분할일에 -50% 가짜 손실이 찍힌다 |
| 가격 캐시는 **덮는다** (뉴스와 반대) | 수정주가가 바뀌는 건 정상이다. 대신 `price_revisions`에 이력을 남기고, `close_raw`가 바뀌면 비정상으로 보고 자동으로 덮지 않는다 |
| 장마감 +30분 이후에만 그날 종가 인정 | 늦게 아는 건 안전하고 일찍 아는 건 룩어헤드다 |
| 지수를 `prices` 테이블에 같이 넣는다 | 적중 판정이 지수 대비 초과라 채점기가 둘을 같게 다뤄야 한다. 테이블을 나누면 코드가 갈라진다 |
| 층 1 채점은 비용 차감 전/후를 둘 다 기록 | 기획서 7절의 "통제 전/후를 둘 다 싣는다" 태도와 일관 |

### 알아둘 것

**적중 판정이 절대수익이 아니라 지수 대비 초과**(9.1절)라서, 지수 시계열이 어댑터의
1급 요구사항이다. 종목 가격만 받으면 채점 자체가 성립하지 않는다. 처음에 이걸
놓칠 뻔했다.

## 가격 어댑터 구현 — 실측이 설계를 두 번 반증했다

`docs/harness.md` 6절의 미정 다섯 가지를 먼저 확인하고 구현에 들어갔다.

### 확인한 것 (2026-09-16)

| 항목 | 결과 |
|---|---|
| DeepSeek 오프피크 | 피크는 **UTC 01–04, 06–10(평일)뿐**. KST 02:00도 07:00도 **둘 다 오프피크**다 |
| KOSPI200 | pykrx `get_index_ohlcv`가 `KeyError: '지수명'`으로 깨졌다. FDR `KS200`은 정상 |
| KR 거래세 | 기획서 0.18%는 **낡았다.** 2026년 환원으로 코스피 0.05%+농특세 0.15% = **0.20%**, 코스닥도 0.20% |

**실행 시각 이동에 비용이 안 든다**는 게 제일 반가운 결과다. 정합성과 비용을 맞바꿔야
할 줄 알았는데 그럴 필요가 없었다. → KST 07:00~08:00로 확정.

pykrx는 가격 경로에서 뺐다. 지수가 깨졌고, 종목 조회도 호출마다 KRX 로그인 경고가
뜬다. 지금 되는 것도 언제 막힐지 모른다. **수급 데이터(투자자별 매매동향) 용도로만
남긴다** — 그건 FDR이 못 준다.

### 정정 1 — `close_raw`는 미수정가가 아니었다

설계 문서에 "`close_raw`에 실제 거래가가 오고, 미수정으로 계산하면 분할일에 -50%
가짜 손실이 찍힌다"고 썼다. **틀렸다.**

NVDA 10:1 분할(2024-06-10) 전후를 실제 데이터로 봤다.

```
2023-10-02  close_px  44.78     <- 그때 실제 거래가는 약 447달러
2024-06-07  close_px 120.89
2024-06-10  close_px 121.79     <- 분할일에 점프가 없다
35% 이상 일일 변동: 없음
```

**yfinance도 FDR도 분할을 시계열 전체에 소급 적용한 값만 준다.** 미수정 실거래가는
이 벤더들로 얻을 수 없다. 두 열의 실제 차이는 분할이 아니라 **배당**이었다.

| 종목 | 3년 전 시점 두 계열의 괴리 |
|---|---|
| XOM (고배당) | +10.36% |
| NVDA (저배당) | +0.30% |
| 삼성전자 (FDR) | +0.00% |

열 이름을 `close_raw`/`close_adj` → **`close_px`/`close_tr`**로 바꿨다.
`_raw`/`_adj`는 "미수정/수정"으로 읽혀 오해를 부른다. 이름이 거짓말을 하면 나중에
누군가 그대로 믿고 쓴다. 가격은 다시 받을 수 있으므로 테이블을 지우고 재적재했다
(뉴스 테이블은 건드리지 않았다).

### 정정 2 — 초과수익 기준이 틀렸다 (이쪽이 더 심각하다)

문서는 "등락률은 `close_adj`로 계산"이라고 했다. 그런데 벤치마크 `^GSPC`와 `KS200`은
**배당 미포함 가격지수**다. 종목만 배당 조정한 계열로 초과수익을 재면 고배당주가
배당수익률만큼 공짜 점수를 얻는다.

XOM 3년 실측:

```
XOM 가격수익률   +43.9%      총수익률  +58.8%
S&P500(가격지수) +70.3%

초과수익  가격 기준  -26.4%      총수익 기준  -11.5%     <- 14.9%p 차이
```

**14.9%p면 판정이 뒤집힌다.** 배당주 전체에 걸린 계통 편향이라 표본을 늘려도 사라지지
않는다. → 층 1의 초과수익·적중 판정은 **종목과 지수 모두 `close_px`**로 통일했다.

이걸 구현 전에 못 잡았다면 채점 결과 전체가 조용히 오염됐을 것이다. 저울을 먼저
만들자는 기획서 0절 원칙 3이 맞았다는 증거이기도 하다.

### 정정 3 — 벤더 응답을 부분 수용하면 행이 어긋난다

테스트를 쓰다 발견했다. 처음 구현은 `close_px`가 바뀌면 거부하면서 같은 응답의
`close_tr`은 받아들였다. **못 믿는 응답에서 한 열만 골라 받으면 행이 내부적으로
어긋난다.** 둘 다 보류하도록 고쳤다.

## 주간 스케줄 — 시그널이 이제 저절로 쌓인다

기획서 9.1절이 요구한 주 1회 고정 요일·시각을 launchd에 걸었다.

```
com.ys.mastrade.collect    매시 5분        RunAtLoad=true
com.ys.mastrade.baseline   매주 수 07:00    RunAtLoad=false   <- 새로 추가
```

### 수요일 07:00 KST를 고른 이유

- **07:00** — US/KR 기준가가 대칭이 되는 구간이다(`harness.md` 2절). 실데이터로
  확인했다: 02:00에 돌리면 KR은 09-15, US는 09-14가 기준일이 된다
- **고정 요일** — 요일이 흔들리면 구간 간 비교가 깨진다(9.1절)
- 둘 다 DeepSeek 오프피크(피크는 UTC 01–04, 06–10)라 비용도 절반이다

### 주간 작업에만 필요한 장치 셋

수집(매시)과 달리 여기서만 생기는 문제들이다.

**1. 늦게 깨어나면 요일이 밀린다.**
launchd는 잠든 사이 밀린 실행을 깨어날 때 돌린다. 그때 "오늘 07:00"을 as_of로 쓰면
금요일 시그널이 된다. `--weekly`가 **직전 수요일 07:00으로 스냅**한다 — 금요일에
깨어나도 수요일 시점 데이터로 판단하므로 룩어헤드도 없다. 실제 실행 시각은
`runs.started_at`에 따로 남아 얼마나 늦었는지 알 수 있다.

```
수 07:00 정시        -> as_of 수 07:00
금 10:00 (이틀 늦음) -> as_of 수 07:00
월 23:00 (닷새 늦음) -> as_of 수 07:00
```

**2. 중복 실행은 돈이자 표본 오염이다.**
따라잡기와 수동 실행이 겹치면 같은 시점을 두 번 돌 수 있다. 시그널이 중복되면
표본 수가 부풀고 채점이 오염된다. `SignalStore.has_successful_run`으로 같은
(종류·시장·시점)이 이미 성공했으면 건너뛴다.

**3. `RunAtLoad=false`.**
수집은 `true`로 뒀지만 베이스라인은 돈이 나간다(1회 약 $0.5). 로그인마다 부를 이유가
없고, 밀린 실행 따라잡기는 `StartCalendarInterval`이 이미 해 준다.

### 검증

## 비교군 — 룰 기반 비LLM 베이스라인

기획서 2절이 FinRL을 비LLM 베이스라인으로 지목했는데, 그 앞에 더 기본적인 것이 있다.
**LLM이 20줄짜리 룰을 이기는가.** 못 이기면 LLM 자체가 의미 없다.

전략 여섯을 만들어 3년치로 돌렸다 (`src/eval/strategies.py`, `docs/baselines.md`).
방향은 횡단면 순위로 정한다 — 채점이 지수 대비 초과수익이므로 "오를까"가 아니라
"다른 종목보다 나을까"를 맞혀야 한다.

### 겹침을 보정하니 그림이 뒤집혔다

명목 1,695건으로는 KR 모멘텀이 +1.5%로 좋아 보였다. 그런데 주 1회 시그널을
20거래일로 채점하면 인접 표본이 **4배 겹친다.** 날짜별 평균을 관측 1건으로 묶고
20일은 4주 간격으로 솎아 다시 재니:

```
KR   유의한 것 없음 (최고가 ma_gap_120d 5일 t=1.67, 10% 수준)
US   buy_and_hold  5일 t=+2.63 **   20일 t=+2.28 **
     momentum_20d  5일 t=-2.25 **
     ma_gap_120d   5일 t=-2.12 **
     low_vol       5일 t=-2.10 **
     momentum_60d 20일 t=-2.11 **
```

**US에서 유의한 것들이 대부분 음수다.** `buy_and_hold`만 양수고 횡단면 룰들은
음수다 — 유니버스 15종목 전체는 S&P500을 이겼는데, 그 안에서 순위를 매겨 사고파는
것은 손해였다.

명목 표본을 그대로 믿었다면 "KR 모멘텀이 통한다"는 틀린 결론을 냈을 것이다.
앞서 확신도 검정력을 계산하면서 겹침 문제를 먼저 짚어둔 것이 여기서 값을 했다.

### 같은 룰이 두 시장에서 정반대다

| | KR | US |
|---|---|---|
| 모멘텀 계열 | 양수(유의하지 않음) | **음수(유의)** |
| `reversal_5d` | 음수 | 양수 |
| `buy_and_hold` | −1.82% | **+0.79%(유의)** |

기획서 12절의 "같은 구조가 두 시장에서 어떻게 다르게 작동하는가"가 **룰 단계에서
이미 갈린다.** 에이전트를 붙이기 전부터 시장 차이가 있다는 뜻이라, 나중에 LLM
성적이 갈렸을 때 "구조 때문"인지 "시장 때문"인지 분리할 기준선이 생겼다.

### LLM이 넘어야 할 기준선이 정해졌다

- **KR — 지수 대비 0.** 유의하게 작동한 룰이 없다. LLM이 유의한 양수를 내면 그 자체가 결과다
- **US — `buy_and_hold` +0.79%/20일.** 까다롭다. **아무 판단도 하지 않는 전략**이
  유의하게 이긴 구간이었다. LLM이 종목을 고르는 행위 자체가 가치를 더하는지가 시험대다

### 확신도 상관은 룰에서도 0이었다

순위 기반의 **정의가 명확하고 폭이 넓은 확신도**(0.50~0.95)조차 수익을 예측하지
못했다(스피어만 −0.105~+0.088). LLM 확신도(0.42~0.62)가 좁은 것이 걱정이었는데,
**그 지표 자체가 원래 잡기 어려울 수 있다**는 쪽 근거가 생겼다. 0이 나와도
"LLM이 못했다"로 바로 읽으면 안 된다.

### 믿을 때의 한계

다중검정이 가장 크다. 24개 조합을 봤고 5% 수준이면 우연히 1.2개가 유의하다.
6개가 나왔으니 전부 우연은 아니지만 **Bonferroni(|t|>3.1)로는 하나도 안 남는다.**
개별 항목을 강하게 주장하지 않는다. 단일 구간이라는 것, 유니버스가 시점 기준
구성종목이 아니라 생존 편향이 있을 수 있다는 것도 문서에 적었다.

## 확장 방향 검토 — 기획서 14절로 남겼다

"전체 시장에서 오를 종목을 찾는 데까지 갈 수 있나", "단기 스윙도 커버되나"를 검토했다.
**둘 다 3개월 검증 이후 과제로 미뤘고**, 나중에 다시 계산하지 않게 근거 수치를
기획서 14절에 적었다.

### 전체 시장 — 막는 것은 비용이 아니었다

KOSPI 943 + KOSDAQ 1,820 = 2,763종목. 자원은 전부 여유가 있다.

```
LLM 1차 스크리닝(flash)   회당 약 $0.8
LLM 심층(상위 30, v4-pro) 회당 약 $0.5
네이버 뉴스               계층화 시 5,300 / 25,000
가격 저장                 약 200MB
```

기획서 8절의 2단계 구조가 이미 이 모양이고 유니버스는 설정 파일 하나다.
**진짜 선행 조건은 평가 쪽 셋이다.**

1. **선택 편향** — 2,763개에서 30개를 고르면 고른 것만 채점된다. 스크리너 성능은
   "고른 것의 수익"이 아니라 "고른 것과 안 고른 것의 차이"라 전 종목 점수를
   방향 없이 저장하는 경로가 먼저 필요하다
2. **시점 기준 구성종목** — `FDR.StockListing`은 현재 상장 목록만 준다. 과거 시점
   목록을 구할 방법이 없고, 그대로 가면 생존 편향이 정면으로 들어온다
3. 유니버스를 바꾸면 성적 비교가 끊긴다

### 단기 — 앞서 한 말을 정확히 해야 했다

확신도 검정력을 볼 때 "매일 돌려도 독립 정보가 안 는다"고 했는데, **그건 호라이즌이
시그널 간격보다 길 때 얘기였다.** 1거래일 호라이즌은 매일 내도 겹치지 않는다.

실제로 돌려 확인했다 — 같은 구간에서 **독립관측이 113 → 564로 5배** 늘었다.
그리고 **일봉만으로 동작한다.** 인트라데이 데이터가 필요 없다.

```
US buy_and_hold  1일 호라이즌  주1회 113관측 t=3.01 **
                              매일  564관측 t=2.12 **
```

부수 효과가 크다. 20거래일 호라이즌은 3개월에 독립 구간이 3개뿐이라 확신도-수익
상관의 검정력이 약한데, **1거래일이 그 문제를 상당 부분 푼다.**

다만 **지금 붙이지 않는다.** 호라이즌을 중간에 바꾸면 그 전후 성적을 섞을 수 없다
(기획서 7절). 3개월 전진 검증을 끝내고 붙인다.

### 일중은 안 된다 — 세 겹으로 막힌다

| 막는 것 | 실측 |
|---|---|
| KR 인트라데이 과거 | FDR 일봉만, pykrx 분봉 API 없음. **무료로 구할 방법이 없다** |
| US 인트라데이 | yfinance 1분봉 약 30일 / 5분 60일 / 60분 730일 |
| 뉴스 시각 정밀도 | 수집 주기 1시간 → `known_at`이 최대 1시간 늦는다 |
| 체결 모델 | 기획서 9절이 만들지 않기로 명시했다 |

### 변동성은 신호가 아니라 잡음을 키운다

"한국 대형주가 하루 10% 움직이니 기회가 크다"는 직관이 채점에는 반대로 작용한다.

```
초과수익 sd     1일      5일     20일
  KR          2.83%   6.16%  13.24%
  US          1.98%   4.50%   8.79%
연율 변동성 평균  KR 63%  ·  US 35%   (SK하이닉스 122%, Tesla 57%)
```

**같은 실력을 증명하려면 KR이 US보다 약 2배 많은 표본을 요구한다.**
룰 베이스라인에서 KR에 유의한 전략이 하나도 없었던 것도 룰이 나빠서가 아니라
잡음이 커서일 수 있다. 한국장 결과를 해석할 때 이걸 함께 적어야 한다.
