수집 상태를 점검하다 **가격 쪽이 통째로 비어 있던 것**을 찾았다. 채점이 늦어진 정도가

## 문제와 원인

### A. 가격 수집이 **어느 launchd 작업에도 없었다** (가장 큰 피해)

- **증상**: `health_check`가 "마지막 봉 2026-09-17 (11일 전)". 시그널 53건 전부
  `stale`로 채점 0건.
- **확인한 사실**: `run_collect.sh`는 `collect_news.py`만, `run_baseline.sh`는
  `run_baseline.py`만 부른다. **`collect_prices.py`는 어느 래퍼에도 없다.**
  지금까지 들어온 봉은 전부 내가 손으로 돌린 것이었다.
- **원인**: 9월 16일에 스케줄러를 짤 때 뉴스(영구 손실)와 시그널(비용)만 작업으로
  세웠다. 가격은 "나중에 다시 받을 수 있다"는 성질 때문에 급하지 않다고 보고
  **작업 목록에서 빠뜨렸다.** `install_scheduler.sh` 주석이 "작업 두 개"로 시작하는데
  실제로는 세 개를 등록하고 있었다 — 그 불일치도 못 봤다.

**피해가 채점 지연에서 끝나지 않았다.**

```
09-23 회차 시그널 23건 → 기준일 KR 2026-09-17 / US 2026-09-16
                        as_of는 09-23. 닷새~이레 묵은 종가와 지표로 판단했다
```

as-of 규율이 깨진 것은 아니다 — **미래 정보가 샌 게 아니라 정보가 낡았다.**
채점기가 `misaligned`로 걸러냈다. 방어선은 설계대로 작동했고, 걸러내 준 덕에 알았다.

> **교훈**: 09-18 일지에 "안전장치가 반대로 작동할 수 있다"를 적었는데, 이번엔 반대다.
> **채점기가 자기 입력을 의심한 덕에 상위 단계의 누락이 드러났다.** 판정을 거부하는
> 상태(`misaligned`)를 따로 둔 것이 값을 했다. 0으로 채웠으면 못 봤다.

### B. FinanceDataReader의 한국 **지수** 계열이 죽었다

- **증상**: 개별주는 09-23까지 들어오는데 KOSPI200만 09-17에서 멈췄다.
- **확인한 사실** (2026-09-28 직접 조회):

```
FDR  KS200 / KS11 / KQ11      09-18 이후 0행 → 이후 3년 구간 전체가 빈 응답
FDR  개별주 · 069500(KODEX 200)  09-28까지 정상
```

  같은 벤더, 같은 함수인데 **지수 엔드포인트만** 나갔다. 오후에는 아예 전 구간
  빈 응답으로 악화됐다 (13:45에는 721행을 주다가 14:07에는 0행).
- **영향**: KR 초과수익의 기준이 없다 → **KR 채점 전면 중단.** US는 정상.

대체안을 저장된 KS200 3년치와 비교해 실측했다.

| 후보 | 일간 상관 | 20거래일 차이 표준편차 | 계통 편차 | 최대 차이 |

### C. 09-23 주간 베이스라인이 23/30으로 끝났고, 재시도 경로가 없다

```
KR 13/15  실패 LG에너지솔루션 · 삼성바이오로직스      APITimeoutError
US 10/15  실패 AAPL MSFT GOOGL AMZN META           APITimeoutError

- **원인 확인**: `pmset -g log`로 잡았다. 뚜껑 닫힌 배터리 상태에서
  **DarkWake 7초 뒤 재취침**이 계속됐다 (오늘 11:06:25 깨움 → 11:06:32 취침).
  프로세스는 죽지 않고 얼어붙었다 깨어나기를 반복한다. 그 사이 HTTP 요청이 타임아웃 난다.

  이미 적어둔 한계가 그대로 나타났다.
- **가드의 부작용**: "이미 돌렸습니다"가 **부분 성공도 완료로 처리한다.** 그 7건은
  as_of가 지나 되살릴 수 없다.

같은 원인으로 오늘 11시·12시 한국 장중 수집도 비었다 (13:20 뚜껑 열림 후 정상 복구).

### D. 열린 gap 4건 — 인과 사슬이 있다

```
09-22 12:15 KST  DNS 실패 2건 (삼성전자, NAVER)
      ↓ 7시간 공백

취약하다** — 한 번 놓치면 따라잡지 못한다. 삼성전자·NAVER가 매번 같은 자리에 걸린다.

## 결정

### 1. 가격 수집 — 베이스라인 선행 단계 + 일 1회 독립 작업

두 피해가 서로 다른 것이라 처방도 둘이다.

| 피해 | 처방 |
|---|---|
| 시그널 오염 (기준가가 묵음) | `run_baseline.sh`가 **시그널 직전에** 가격을 받는다 |
| 채점 지연 | `run_prices.sh` 일 1회 (17:00 KST + 네트워크 연결 시) |

기각한 대안: **매시 수집에 붙이기.** 벤더 호출이 24배 늘고, 장중 미완결 봉을 계속
던지게 된다. 가격은 뉴스와 달리 영구 손실이 아니므로 그 비용을 낼 이유가 없다.

### 2. 게이트는 **종목 신선도**로 판정한다 — 수집기 종료코드가 아니라

처음엔 `collect_prices.py`의 종료코드로 베이스라인을 막게 짰다. **바로 틀렸다.**
등록 직후 실행에서 KOSPI200 하나가 실패해 종료코드 1이 나왔고, 그대로 뒀으면
**FDR 지수 장애가 지속되는 동안 주간 베이스라인이 영원히 스킵됐을 것이다.**

`--check-fresh DAYS`를 새로 만들었다 — 호출 없이 저장된 봉만 보고 **종목**이 최신인지
판정한다. 지수는 보지 않는다.

```
지수가 막혔다  →  채점만 미뤄진다 (백필 가능)        →  시그널은 낸다
종목이 묵었다  →  오염된 시그널이 나온다 (복구 불가)  →  시그널을 내지 않는다
```

> **오염된 표본보다 없는 표본이 깨끗하다.** `--weekly`가 as_of를 같은 수요일로
> 스냅하므로, 주 안에 다시 깨어나면 같은 시점으로 재시도한다.

`run_prices.sh`의 종료코드도 같은 기준으로 바꿨다. 지수 실패로 스탬프를 못 찍으면
네트워크가 바뀔 때마다 32종목을 다시 받는다 — 벤더 장애가 길어지면 하루 종일 그런다.

### 3. KOSPI200은 **며칠 기다린다**

- **가격은 뉴스와 달리 백필된다.** 09-18~09-23 네 거래일은 FDR이 복구되면 자동으로
  메워진다. 지금 계열을 바꾸면 `docs/baselines.md`의 3년 기준선을 전부 다시 깔아야 하고,
  ETF는 연 −2.04%p 계통 편차를 초과수익에 심는다.
- `health_check`에 **"벤치마크 지수"** 항목을 새로 넣었다. 지수가 종목보다 1일 넘게
  뒤처지면 경고한다. **이 항목이 OK로 돌아오는 순간이 벤더 복구 시점이고, 그때 백필한다.**
- 이 점검이 없어서 못 봤다. 전체 최신 봉만 보면 종목 날짜에 가려 안 보인다.

### 4. 09-23 부분 실패 7건 — 기록만 남긴다

원인이 노트북 잠자기라 코드로 못 막는다. 타임아웃·재시도를 늘리면 2.5일짜리 실행을
더 길게 만들 뿐이다. **상시 전원 기기로 옮길 때 같이 푼다.**

### 5. (덤) 장중 구멍 판정에서 **진행 중인 시간**을 뺀다

수집기는 종목별 주기를 보고 "아직 안 됐다"면 회차 기록을 남기지 않는다. 14:11에
점검하면 13:18에 다 받아둔 상태여도 14시가 빈 것으로 보인다.
**매일 거짓 경보가 뜨면 진짜 구멍을 흘려보낸다.**

## 결정 — 넷 중 둘만 가져온다

### 가져온 것 1. DSR + PBO — 우리 설계에 실재하던 구멍

`validation.md` 5.3절에 "조합 1,116가지를 LLM 호출 0회로 탐색"이라고 써뒀다.
**그게 정확히 백테스트 과최적화의 교과서적 상황이다.** 1,116개를 다 계산하고 최고를
고르면 그 최고는 실력이 아니라 최댓값 통계일 수 있다.

나는 **새 호출이 드는 8아암에만 Bonferroni를 걸어두고, 공짜라서 매력적이라던
1,116개는 보정 없이 비워뒀다.** 공짜인 쪽이 위험은 더 큰데 그걸 못 봤다.

`src/compute/metrics.py`에 둘을 넣고 합성 데이터로 교정했다.

```
잡음만 1,116 시행 → 최고 샤프 +0.485  DSR 0.71   (0.95 미달 — 우연으로 걸러진다)
진짜 엣지 심었을 때  샤프 +0.550  DSR 0.84
PBO  엣지 없음 30셋 평균 0.500 (표준편차 0.165) · 엣지 1개 30셋 평균 0.142
```

**PBO 한 번의 값을 정밀하게 읽으면 안 된다**는 것도 같이 재서 남겼다 — 조합들이 같은
데이터를 공유해 독립이 아니라 단일 데이터셋 표준편차가 0.165다. 문서에는 그 말이 없다.

### 가져온 것 2. 모든 보고에 신뢰구간

오늘 오후에 US 5거래일 적중률 0.444를 보고하면서 "n=15라 해석하지 않는다"를
**말로** 덧붙였다. 말은 다음 사람에게 전달되지 않는다. 이제 자동으로 찍힌다.

```
5거래일  채점 15/25  적중률 0.444[0.19,0.73]~  비용후 -1.22%[-4.91,+2.87]%p
                                        ↑ 구간이 0.5를 품는다 = 동전과 구분되지 않는다
```

적중률은 Wilson 구간(정규 근사는 표본이 작을 때 [0,1]을 벗어난다), 평균초과는 t 구간
(n=15에서 z를 쓰면 구간을 10% 좁게 잡는다 — Cornish-Fisher 전개로 scipy 없이 구했다).

### 문서 자체의 한계 — 학습 룩어헤드가 없다

`skill.md`의 16항목은 **데이터 룩어헤드만 다룬다.** LLM 시스템에는 워크포워드로 못 푸는
종류가 따로 있다 — 모델 가중치가 이미 그 구간을 봤다는 것. 09-21 일지에 정리한 구분이다.
**이 체크리스트를 그대로 검증 게이트로 쓰면 그 위험이 통째로 시야에서 사라진다.**

그리고 `skill.md`는 마지막에 자기 회사 도구(`bar-by-bar`, `edgehunt`)를 홍보한다.
게이트를 외부에 맡기는 대신 **항목을 우리 문서로 옮기고 자동 판정 가능한 것부터
테스트로 만드는** 쪽을 택했다 — 192개 테스트가 이미 그 역할이다.

## 문제와 원인 — 테스트가 잡은 부동소수점 버그

- **증상**: `deflated_sharpe(0.5, [0.1, 0.1, 0.1], 60)`이 None이 아니라
  **0.9998**("엣지가 있을 확률 99.98%")을 돌려줬다.
- **원인**: `stdev([0.1, 0.1, 0.1])`이 0이 아니라 **1.7e-17**이다. 부동소수점 잡음인데
  `sd == 0` 가드를 그냥 통과한다. 같은 함수에 `0.01`을 세 번 넣으면 정확히 0이 나와서
  기존 테스트는 통과하고 있었다 — **입력값에 따라 갈리는 가드였다.**
- **해결**: `ZERO_VARIANCE_TOL = 1e-12`를 두고 `sharpe`·`sortino`·`_sharpe_raw`·
  `deflated_sharpe` 네 곳에 적용했다. 수익률은 1e-4 수준이라 진짜 변동을 삼키지 않는다.

**09-18에 가격 수정 이력에서 배운 것과 같은 교훈이다: 등호로 0을 재지 않는다.**
그때는 `rel_tol=1e-9`가 너무 빡빡해 4,744건이 잡음으로 기록됐고, 이번엔 `== 0`이
너무 느슨해 잡음이 통과했다. 방향만 반대다.
