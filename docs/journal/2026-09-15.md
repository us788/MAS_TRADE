## 결정

**유니버스는 시총 상위 10 + 섹터 보완 5, 시장별 15종목.** (`config/universe.json`)

시총 상위 15만 담는 안을 기각했다. 미국이 거의 테크로 채워져 리스크 엔진의 섹터 집중 룰이
매주 발동하고, 에이전트들이 같은 거시 변수를 보게 되어 의견이 비슷해진다. 그러면 논쟁
레이어가 검증 대상이 아니라 장식이 된다. 보완 5종목은 에너지·헬스케어·필수소비재·산업재·
유틸리티에서 채웠다. 결과는 미국 섹터 9개, 한국 12개.

직접 지정안도 기각했다. 관심 종목을 고르면 선택 자체에 선입견이 들어가 시스템 성적과 섞인다.

> 시총 순위는 네트워크 차단으로 실시간 확인을 못 했다. 수집 착수 전 검증 필요.

**종목 교체는 changelog에 날짜와 이유를 남긴다.** 유니버스를 조용히 바꾸면 성적 비교가 깨진다.

**뉴스 수집기를 다른 무엇보다 먼저 만든다.** 가격·공시·매크로는 나중에도 과거를 조회할 수
있지만 뉴스 아카이브는 살 수 없다. 오늘 안 받으면 오늘이 영영 빈다. 되돌릴 수 없는 손실은
이것뿐이라 1순위.

**SEC EDGAR는 보류.** 접속이 막혀 원인 규명에 시간을 쓰는 대신 나머지 파이프라인을 먼저 만든다.
EDGAR가 빠져도 뉴스 파이프라인은 온전히 돌아가고, 재무는 주간 판단에 매일 필요하지 않다.

## 문제와 원인

**API 인증 스모크 테스트 8건 중 7건 통과, SEC EDGAR만 403.**

확인한 사실:

- `SEC_USER_AGENT`는 `MAS_TRADE usang01@naver.com` (27자). SEC 공식 문서의 예시
  `Sample Company Name AdminContact@<domain>.com` 와 같은 형태다. `.env` 파싱도 정상
- 헤더 변형 6가지(UA 단독 / Accept·Host 추가 / 언더스코어 제거 / 대괄호 이메일 /
  브라우저형 UA)가 **전부 동일하게 403**
- **같은 IP에서 브라우저로는 JSON이 정상 조회된다.** VPN 미사용
- `data.sec.gov`와 `www.sec.gov`의 거부 메시지가 다르다
  - `data.sec.gov` → "Your Request Originates from an Undeclared Automated Tool"
  - `www.sec.gov` → "Request Rate Threshold Exceeded"

원인: **미상.** 두 가지 가설이 있고 아직 가르지 못했다.

1. *클라이언트 지문 가설* — SEC 앞단(Akamai)이 TLS/HTTP2 지문으로 파이썬 클라이언트를
   걸러낸다. 브라우저 UA를 써도 막힌 것이 이 가설에 맞는다.
2. *IP 평판 가설* — 요청을 몇 번 안 보냈는데 `www.sec.gov`가 "Rate Threshold Exceeded"를
   돌려준 것은 **이미 플래그된 IP**라는 뜻일 수 있다. 통신사 공용 IP의 여파 가능성.

> **정정.** 처음에 1번 가설을 확신조로 말했는데 과했다. `requests`에 UA만 붙여 `data.sec.gov`를
> 쓰는 사례는 흔하고 보통 동작한다. 2번을 먼저 배제하지 않은 채 단정한 것이 잘못이었다.

미확인: 전송 계층 비교(requests 완전 헤더 / curl / httpx HTTP2 / curl_cffi). 스크립트는
`scripts/diagnose_sec.py`에 있고 IP 차단이 풀린 뒤 돌려야 결과가 깨끗하다.

**`clean_text`가 문장부호 앞에 공백을 남겼다.** `<b>` 태그를 공백으로 치환해서
`<b>삼성전자</b>,` 가 `삼성전자 ,` 로 나왔다. 네이버가 검색어를 `<b>`로 감싸 보내기 때문에
한국 기사 제목 대부분이 이 꼴이 될 뻔했다. 테스트에서 잡혔다.

**작업 환경에서 대상 호스트가 전부 차단된다.** 세션 프록시의 허용목록에 `sec.gov`,
`finnhub.io`, `api.deepseek.com` 등이 없다. `pypi.org`·`github.com`은 열린다.
API 호출이 필요한 검증은 로컬 터미널에서 직접 돌려야 한다.

## 해결

- `f0c208d` 뉴스 수집 파이프라인 — 스토리지, US/KR 어댑터, 유니버스, 테스트 30건
  - `clean_text`: 인라인 태그는 제거하고 블록 태그(`<br>` 등)만 공백으로 치환
  - 태그 제거를 엔티티 해제보다 **먼저** 한다. 순서를 바꾸면 `&lt;b&gt;` 같은 리터럴
    텍스트가 진짜 태그가 되어 지워진다
- `known_at` 도입: 평소에는 발행 시각을 쓰되 그것이 수집 시각보다 미래면 벤더 값이 깨진
  것이므로 수집 시각을 쓴다. 늦게 알았다고 보는 쪽이 룩어헤드에 안전하다
- `content_hash` 중복 제거: 같은 기사가 여러 날 검색에 걸리는 일이 흔한데 그대로 쌓으면
  센티먼트 집계가 기사 수에 끌려간다. 단 한 기사가 두 종목에 걸리면 종목별로 1건씩 남긴다
- 수집 실패를 `logs/collection_gaps.jsonl`에 기록해 재시도 대상으로 남긴다.
  조용히 넘어가면 그날 구멍을 영영 모른다

## 추가 — 네이버 검색 실측 (오후)

어댑터를 실제로 돌려보니 설계 가정 두 개가 틀렸다. **테스트 30건이 전부 가짜 데이터라
잡히지 않았던 것들이다.**

### 문제 1 — 관련성 필터가 무력했다

`get_news('005930', ..., require=['삼성전자'])` 결과가 **정확히 100건**(display 상한)이었다.
한 건도 안 걸러졌다는 뜻이다. 제목은 "디지털 유산 정리 제도화 필요", "AI글래스 생태계" 같은
삼성전자와 무관한 일반 IT 기사였다.

원인: **네이버는 본문까지 매칭하는 키워드 검색이고, 반환하는 스니펫(`description`)은
매칭 지점 주변이라 검색어가 거의 항상 들어 있다.** 그래서 "종목명이 제목+요약에 있는가"로
거르면 100% 통과한다. 필터가 돌기는 하는데 아무 일도 하지 않았다.

실측 (종목당 1,000건 표본):

| | 삼성전자 | 한화에어로스페이스 |
|---|---|---|
| 제목에 종목명 | 184건 (18%) | 232건 (23%) |
| 요약에만 | 816건 (82%) | 753건 (75%) |
| 둘 다 없음 | 0건 | 15건 (2%) |

필요했던 것은 "언급됐는가"가 아니라 **"이 기사가 그 종목에 관한 것인가"** 였다.

### 문제 2 — 1,000건이 덮는 시간이 종목마다 27배 차이 난다

`start` 상한이 1,000이라 한 번에 최대 1,000건인데, 그 1,000건이 덮는 구간은
언급 빈도에 반비례한다.

| 종목 | 벤더 집계 | 1,000건이 덮는 구간 |
|---|---|---|
| 삼성전자 | 446만 건 | **7.0시간** |
| 한화에어로스페이스 | 18만 건 | **192.5시간 (8일)** |

하루 1회 수집으로 통일하면 **삼성전자는 매일 17시간이 빈다.** 벤더 제약이라 코드로 못 푼다.

### 결정

**관련성은 버리지 않고 등급으로 저장한다.** `relevance` = title / summary / none.
기본 파이프라인은 `title`만 에이전트에 넘기고, `summary`는 저장해 둔다.
나중에 "스쳐 언급도 예측력이 있나"를 **추가 호출 없이 사후 재채점**할 수 있다 —
에이전트 부분집합 ablation과 같은 논리다. 82%를 버리면 그 질문을 영영 못 던진다.

**벤더 태깅 여부를 별도 필드로 둔다.** Finnhub는 티커로 태깅해 돌려주므로 제목 매칭 없이도
1차 자료다. 네이버는 키워드 검색이라 보증이 없다. `vendor_tagged`가 이 차이를 담는다.
`is_primary = vendor_tagged or relevance == "title"`.

**수집 주기를 종목별로 배정한다.** 유입 속도를 재고 3/6/12/24시간 등급을 붙인다.
기준은 1,000건 한도의 **절반(500건)으로 주기를 덮을 수 있는가** — 뉴스가 갑자기 몰려도
버티는 여유다. 실측값 기준 삼성전자 3시간, 한화에어로 24시간.

> 이것은 기획서의 "매일 수집해 쌓는다"를 **"종목별 주기로 수집해 쌓는다"**로 바꾸는 결정이다.

**커버리지 미달을 batch가 보고한다.** `reached_floor=False`면 lookback 구간을 다 못 받았다는
뜻이고, 호출부가 gap으로 기록해 다음 실행에서 메운다. 조용히 넘어가면 구멍을 영영 모른다.

### 해결

- `cac0632` 스크립트 실행 경로 문제 (`python scripts/x.py`가 저장소 루트를 sys.path에
  올리지 않아 `No module named 'src'`)
- `Relevance` 등급, `vendor_tagged`, `is_primary` 도입
- 네이버 어댑터에 페이징 추가 — lookback 경계에 닿을 때까지 최대 10페이지
- `scripts/measure_news_rate.py` — 유입 속도 측정과 주기 배정 (`--apply`로 universe 반영)
- 테스트 36건 (30 → 36)

### 배운 것

**가짜 데이터 테스트는 파서의 정확성은 검증해도 벤더의 의미론은 검증하지 못한다.**
`matches_symbol`은 단위 테스트를 전부 통과했다. 정확히 설계한 대로 동작했고,
설계가 틀렸을 뿐이다. 어댑터는 실제 응답을 한 번 보기 전까지 완성이 아니다.

### 별건 — 기획서가 커밋에 반영되지 않았던 것

`docs/plan.md`의 뉴스 소스 섹션이 `c0dd076`에 들어가지 않은 채로 있었다.
컨테이너 작업 사본(29,669바이트)에는 편집이 있었지만 저장소 파일은 이전 버전(26,590바이트)
그대로였다. 파일 전송 도구가 성공을 반환했고 `git status`도 변경으로 잡았는데 내용은
옛것이었다. 정확한 경위는 불명.

복구는 작업 사본을 다시 밀어 넣어 해결했고, 오늘 변경은 그 위에 얹었다.

**교훈: 파일을 쓴 뒤에는 도구의 성공 응답이 아니라 파일 내용을 확인한다.**
바이트 수나 특정 문구 존재 여부를 한 줄로 검증하면 된다. 이번엔 하루 뒤에야 발견했다.

## 추가 — 15종목 유입 속도 실측 (저녁)

### 문제 — 측정치 두 건이 비현실적이었다

| 종목 | 100건이 덮는 구간 | 쿼리 |
|---|---|---|
| 기아 | 318.7시간 (13일) | `"기아 자동차"` |
| NAVER | 801.4시간 (33일) | `"네이버 주가"` |

둘 다 시총 상위인데 하루 2~3건이 나올 수 없다.

원인: **네이버 검색은 다단어 쿼리를 AND로 묶는다.** 동명이의를 쿼리에서 막으려고
두 단어를 넣었는데, 그건 `news_exclude`가 할 일이었다. 쿼리는 넓게 잡고 배제로 좁혀야 한다.

→ 기아 `"기아"` + exclude `[기아대책, 타이거즈, 프로야구]`, NAVER `"네이버"`로 교정.

### 결정 — 안전 여유를 1/2에서 1/4로

측정 결과 하루 최대 호출이 약 350회였다. **한도 25,000회의 1.4%.** 한도가 전혀 병목이 아니다.
반면 놓친 구간은 영구 손실이다. 비용이 거의 0인 쪽으로 치우치는 것이 맞다.

여유를 1,000건의 1/4(250건)로 잡고 1시간 등급을 추가했다. 삼성전자·SK하이닉스가 1시간으로
내려온다. 이래도 하루 800회 수준이라 한도의 3%다.

측정 시점 편향도 고려했다. **장중에 쟀으므로 야간 속도는 더 낮고 실적 시즌에는 몇 배로 뛴다.**
평균치에 딱 맞춘 주기는 스파이크에서 반드시 뚫린다.

### 미결 — 별칭이 부족한 종목

제목 매칭률이 낮은 종목들이 있다. 검색은 되는데 제목에 쓰는 표기가 `news_require`에 없다는 뜻이다.

| 종목 | 제목 매칭률 |
|---|---|
| LG에너지솔루션 | 5% |
| 삼성바이오로직스 | 8% |
| LG화학 | 10% |
| 삼성전자 | 13% |

측정 스크립트가 15% 미만이면 제목 표본을 출력하도록 했다. 실제 표기를 보고 별칭을 보강한다.

### 교정 후 재측정 — 쿼리 수정은 맞았고, 내 진단 메시지는 틀렸다

**기아 해결.** 318.7시간 / 0.3건/h → **2.8시간 / 35.3건/h**, 제목 매칭 28%.
다단어 AND 가설이 맞았다.

**NAVER는 반대로 갔다.** `"네이버 주가"` → `"네이버"`로 넓히자 유입이 0.1 → 95.2건/h로
폭증했지만 제목 매칭은 33% → **7%**로 떨어졌다. 네이버는 플랫폼이라 온갖 기사가 본문에서
언급한다. 좁으면 굶고 넓으면 잡음인 구조다.
→ `"네이버"` 유지. 제목 기준 하루 160건이 남고, 잡음은 `relevance`가 이미 분리한다.

**내 진단 메시지가 오진을 유도했다.** 제목 매칭률이 낮으면 "별칭 보강"이라고 찍게 해뒀는데,
매칭 안 된 제목을 실제로 보니 원인이 달랐다.

| 종목 | 매칭률 | 매칭 안 된 제목 |
|---|---|---|
| LG화학 | 9% | "고려아연 사태", "500대 기업 여성 임원", "추석 앞두고 5조 원" |
| 삼성바이오로직스 | 8% | "코리아 프리미엄 위크", "제약·바이오 녹색전환", "마감 시황" |

전부 **시황·업계 기사에 본문으로만 딸려 나온 것**이다. 별칭 부족이 아니라
**제목 필터가 정확히 제 역할을 하고 있다.** 5~10%만 남는 것이 정상이고 그게 진짜 그 종목
기사다. LG에너지솔루션도 하루 36건이 남아 충분하다.

→ 스크립트가 **매칭 안 된 제목**을 보여주도록 고쳤다. 앞의 3건을 그냥 찍으면
   매칭된 기사가 섞여 나와 판단을 흐린다.

### 문제 — 측정이 흔들린다

| 종목 | 1차 | 2차 (1시간 뒤) | 차이 |
|---|---|---|---|
| 삼성전자 | 162.2건/h | 122.4건/h | -25% |
| SK하이닉스 | 113.2 | 95.2 | -16% |

100건 표본이라 노이즈가 크고 시간대에 따라서도 달라진다. 주기가 실행할 때마다 바뀌면
곤란하다. 특히 **한산한 시간에 측정해서 주기가 늘어나면 그만큼 구멍이 생기고 되돌릴 수 없다.**

→ `--apply`는 기본적으로 **주기를 줄이기만** 한다. 늘리려면 `--allow-longer`를 명시해야 한다.
   비대칭이 맞다 — 짧게 잡아 생기는 손해는 호출 몇 번이고, 길게 잡아 생기는 손해는 영구 손실이다.

## 저장소를 JSONL에서 SQLite로

### 문제 — 중복 제거 범위가 파일 하나였다

"저장 위치가 종목별 DB인가"라는 질문을 확인하다가 발견했다.

JSONL 레이아웃은 `news/{시장}/{날짜}/{소스}.jsonl`이었고, 중복 검사는 **그 파일 안에서만**
`(종목, content_hash)`로 했다. 삼성전자는 1시간 주기에 lookback 1일이라 같은 기사를
하루 24번 다시 받는데, **자정을 넘기면 날짜 파일이 바뀌어 중복이 그대로 저장된다.**
매일 한 번씩 확실히 발생하는 버그였다.

부수적으로, 중복 검사가 매번 그날 파일 전체를 읽어 해시 집합을 만들었다. 파일이 커질수록
수집이 느려진다.

규모도 문제였다. 고유 기사가 KR만 하루 1.5~2만 건, 1년이면 700만 행에 3GB 안팎이다.
"삼성전자의 지난 20거래일 뉴스"를 뽑으려면 20개 파일을 전부 스캔해야 한다.

### 결정 — SQLite

`(symbol, content_hash)`를 PRIMARY KEY로 두면 **중복이 구조적으로 불가능**해진다.
날짜 경계 문제가 사라지고 중복 검사가 인덱스 조회가 된다.

- `INSERT OR IGNORE`를 쓴다. `INSERT OR REPLACE`가 아니다 —
  **`collected_at`은 최초 관측 시각으로 고정돼야 한다.** known_at의 보수적 판정이 이 값에
  기대므로, 나중에 받은 것으로 덮으면 "언제 알았나"가 뒤로 밀린다
- 인덱스는 `known_at` 기준으로 건다. as-of 조회가 항상 known_at을 쓰기 때문이다
- WAL 모드 — 수집 중에도 읽기가 막히지 않는다
- `collection_runs` 테이블로 마지막 수집 시각을 관리한다. 주기 스케줄러의 근거이자
  커버리지 감사 기록이다
- `schema_version`을 둬서 코드와 DB가 어긋나면 즉시 실패시킨다

**원본 응답은 파일로 남긴다.** 재현성을 위해 쌓아둘 뿐 거의 읽지 않아서 DB에 넣으면
용량만 불린다.

나중에 분석할 때 DuckDB로 SQLite 파일을 직접 질의할 수 있어 막다른 길이 아니다.

> 데이터가 하나도 쌓이지 않은 시점이라 마이그레이션이 필요 없었다.
> 수집을 시작한 뒤였다면 700만 행을 옮겨야 했다.

### 테스트

41건 (36 → 41). 새로 추가한 것 중 핵심은
`test_날짜가_바뀌어도_중복이_생기지_않는다` — 방금 고친 버그를 고정한다.
`test_최초_관측_시각이_유지된다`는 INSERT OR IGNORE을 REPLACE로 바꾸면 깨진다.

## 수집 스크립트 — KR/US 통합

### 결정 — 스케줄을 cron이 아니라 코드가 결정한다

cron은 **한 시간마다 깨우기만** 하고, 어떤 종목을 돌지는 `collection_runs`의 마지막 수집
시각과 종목별 주기를 보고 스크립트가 고른다.

cron에 종목별 스케줄을 흩어 놓으면 주기를 바꿀 때마다 crontab을 고쳐야 하고, 주기의 근거
(실측값)와 실행 설정이 두 곳으로 갈라진다. `universe.json` 한 곳만 보게 둔다.

**US도 같은 스크립트에 넣었다.** Finnhub는 날짜 범위로 직접 조회할 수 있어 커버리지 미달이
구조적으로 없다 — `reached_floor`가 항상 True이고 주기도 24시간 고정이다. 성질이 달라도
호출부가 같으면 cron 하나로 끝난다.

### DUE_SLACK — 경계에서 한 판을 통째로 건너뛰는 문제

1시간 주기인데 cron이 1분 늦게 깨우면 "아직 59분밖에 안 지났다"로 판정되어 **다음 시간까지
밀린다.** 그 한 시간이 통째로 빈다. 5분 여유를 둬서 막았다. 테스트로 고정했다.

### 실패 처리 — 실패한 수집은 이력을 남기지 않는다

`collect_one`은 예외를 올리지 않고 gap으로 기록한 뒤 다음 종목으로 넘어간다. 한 종목이
실패해도 나머지는 계속 돈다.

중요한 것은 **실패 시 `collection_runs`에 기록하지 않는다**는 점이다. 기록하면 "방금 돌았다"로
판정되어 다음 주기까지 재시도하지 않는다. 실패는 곧 재시도 대상이어야 한다.

커버리지 미달(`reached_floor=False`)은 다르다. 수집 자체는 일어났으므로 이력은 남기되
gap도 함께 남긴다. 페이지 상한에 걸렸다는 뜻이므로 주기를 줄여야 한다는 신호다.

### lookback은 주기의 2배

1배면 경계에서 놓친 것을 영영 못 메운다. 2배로 겹쳐 받고 중복은 DB가 막는다.
1시간 주기처럼 짧은 경우를 위해 하한 6시간(0.25일)을 뒀다.

51건 (41 → 51). 스케줄 판정과 실패 처리를 전부 네트워크 없이 검증한다.

## 첫 실전 수집과 거기서 드러난 것

삼성전자 1종목으로 첫 수집을 돌렸다.

```
OK  삼성전자  수집 788 (1차 110) 페이지 8   경계도달 True
DB  773건 · title 107 / summary 666 / none 0
```

**정상 동작 확인.** 1차 자료 표본이 전부 진짜 삼성전자 기사였다 — 주주환원, 중국 대표단
방문, 트럼프·젠슨황 건. 제목 필터가 제 역할을 한다. 제목 매칭 13.8%로 진단 때(13~15%)와
일치. 중복 15건은 같은 실행 안에서 원문 링크가 겹친 것으로, 중복 제거가 작동한다는 증거다.

### 문제 1 — 원본 응답 8페이지 중 1개만 남았다

`save_raw`가 파일명을 `{종목}_{수집시각}.json`으로 만드는데 **수집 시각이 8페이지 내내
같다.** 8개가 서로를 덮어써서 마지막 페이지만 남았다.

원본 전량 저장은 기획서의 재현성 전제다. 파서를 고쳤을 때 되돌릴 수 없게 된다.

→ **수집 1회를 한 단위로 묶는다.** 파일 하나에 `page_count`와 `responses` 배열로 담는다.
   페이지마다 파일을 쪼개면서 이름을 다르게 하는 방법도 있지만, 수집 1회가 재현의 단위이므로
   묶는 쪽이 맞다.

### 문제 2 — lookback 고정 하한이 두 방향으로 틀렸다

10페이지 상한 중 **8페이지를 썼다.** 여유가 2페이지뿐이라 유입이 25%만 늘어도 뚫리고
실적 발표일엔 확실히 뚫린다.

원인은 내가 lookback 하한을 6시간으로 잡은 것이다. 1시간 주기인데 매번 6시간을 받을 이유가
없다. 그런데 반대 방향으로도 틀렸다 — **cron이 몇 시간 멈췄다 살아나면 고정값으로는 그
구간을 못 메운다.**

→ **마지막 수집 시각 기준으로 계산한다.** 경과 시간의 1.5배, 하한 1시간, 상한 7일.
   첫 수집만 기준이 없으므로 주기의 2배.

| 상황 | 이전 | 이후 |
|---|---|---|
| 1시간 주기 정상 | 6.0h (8페이지) | 1.5h (약 2페이지) |
| cron 5시간 중단 | 6.0h (못 메움) | 7.5h (자동 복구) |
| 30일 중단 | 6.0h | 7일 (상한) |

겹쳐 받는 비용은 0이다 — 중복은 DB가 막는다.

### 용량 실측

행당 986바이트. 15종목 전체로 하루 약 14MB, 1년 5GB. SQLite가 감당할 수준이고 로컬
디스크에도 부담은 아니다. 대부분을 `summary` 텍스트가 차지하는데, `relevance='summary'`
기사의 요약을 버리면 줄일 수 있지만 그러면 "스쳐 언급도 예측력이 있나"를 볼 때 제목만
남는다. 지금은 그대로 둔다.

### 테스트

57건 (51 → 57). lookback 다섯 가지 상황과 원본 덮어쓰기 방지를 고정했다.
