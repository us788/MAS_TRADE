# 2026-11-05

## 문제와 원인

### 멈춤 탐지가 거짓 심각을 냈다 — 예고했던 그 오보다

11-04 16:35에 점검이 심각을 띄웠다.

```
!! 스케줄러   baseline 9시간째 실행 중 (pid 32125) — 멈춘 듯하다
```

- **확인한 사실**: 같은 순간 그 프로세스는 **최근 1시간에 LLM 호출 25건**을 하고
  있었고, 마지막 호출이 **141초 전**이었다. 멈춘 게 아니라 **노트북이 자는 동안
  얼어 있다 깨기를 반복**했을 뿐이다. 그날 회차는 결국 US 15/15로 끝났다.
- **원인**: 10-07에 넣은 `check_scheduler`가 `ps -o etime`, 즉 **벽시계**로
  "얼마나 오래 떠 있나"를 봤다. 그런데 벽시계로는 가를 수 없다.

```
10-07  진짜 멈춤 (nslookup)        벽시계 7일
10-14  정상 회차 (자다 깸)          벽시계 7시간 51분
11-04  정상 회차 (자다 깸)          벽시계 9시간 49분
```

**임계값을 어디 두든 한쪽이 틀린다.** 4시간이면 10-14·11-04가 오보고,
10시간으로 올리면 11-04는 통과하지만 다음에 12시간짜리 정상 회차가 또 걸린다.

10-15 일지 미결에 *"정상 회차가 도는 중에 점검이 겹쳤으면 심각 오보가 났을 것이다 —
시작 전·종료 후에 돌아 우연히 안 겹쳤다"*고 적어뒀다. 3주 만에 겹쳤다.

## 해결

**판정 기준을 "얼마나 오래 떠 있나"에서 "얼마나 오래 아무것도 안 했나"로 바꿨다.**

진행 흔적은 이미 DB에 있다 — 각 작업만 쓰는 테이블이다.

| 작업 | 진행 신호 |
|---|---|
| `baseline` | `llm_calls.called_at` |
| `collect` | `collection_runs.ran_at` |
| `prices` | 없음 → 벽시계로 판단(보수적) |

```python
def _stuck_verdict(elapsed_seconds, idle_seconds):
    if elapsed_seconds is None or elapsed_seconds <= STUCK_JOB_SECONDS:
        return False
    if idle_seconds is None:
        return True          # 흔적이 없으면 보수적으로 멈춤
    return idle_seconds > NO_PROGRESS_SECONDS
```

`NO_PROGRESS_SECONDS = 30분`. LLM 호출 간격이 수십 초~수 분이라 여유가 충분하다.

**재판정 확인**

```
11-04 상황  elapsed 9h49m · idle 141초   →  False  (오보가 사라진다)
10-07 상황  elapsed 7일   · idle 7일     →  True   (진짜 멈춤은 그대로 잡힌다)
```

테스트 215 → 221. 실측 세 건(10-07·10-14·11-04)을 그대로 테스트로 박았다 —
**느슨하게 만든 대가로 진짜를 놓치지 않는지가 핵심이라** 10-07 케이스를 같이 묶었다.

- **디스크가 16GB까지 내려왔다.** 10-25 19GB → 11-05 16GB. 속도가 붙었다
