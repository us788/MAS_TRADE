## 1순위 — 시그널이 실제로 쌓이는지 확인

**주간 스케줄을 걸었다** (2026-09-16). 이제 사람이 안 눌러도 시그널이 쌓인다.

```
com.ys.mastrade.collect    매시 5분
com.ys.mastrade.baseline   매주 수 07:00  + 네트워크 연결 시   (주 1회만 실제 실행)
com.ys.mastrade.health     매일 08:30    + 네트워크 연결 시   (하루 1회만 실제 점검)
```

**노트북은 정해진 시각에 켜져 있지 않다.** 그래서 시계는 보조이고, 주 트리거는
**뚜껑을 열어 Wi-Fi가 붙는 순간**이다 (`LaunchEvents` / `network_change`).
네트워크가 **끊길 때도** 발화하므로 래퍼가 DNS 준비를 최대 30초 기다리고,
하루(주) 1회 가드가 중복 실행을 막는다.

**다음 발화는 2026-09-23(수) 07:00 KST다.** 그날 이후 이것부터 본다.

```bash
scripts/run_baseline.py --status     # 시그널이 15→30건씩 늘고 있는가
scripts/score_signals.py             # 채점 (pending이면 아직 안 지난 것)
tail -20 logs/baseline.log
scripts/install_scheduler.sh --status
```

**왜 07:00 수요일인가**

- **07:00** — US/KR 기준가가 대칭이 되는 유일한 구간이다(`harness.md` 2절).
  02:00에 돌리면 US만 기준일이 하루 밀린다. DeepSeek 오프피크이기도 하다
- **고정 요일** — 기획서 9.1절. 요일이 흔들리면 구간 간 비교가 깨진다

**늦게 깨어나도 요일은 유지된다.** `--weekly`가 as_of를 직전 수요일 07:00으로
스냅한다 — 금요일에 깨어나도 수요일 시점 데이터로 판단한다(룩어헤드 없음).
실제 실행 시각은 `runs.started_at`에 따로 남으므로 얼마나 늦었는지는 거기서 본다.

**중복은 구조적으로 막힌다.** 같은 (종류·시장·시점)을 이미 성공했으면 건너뛴다.
launchd 따라잡기와 수동 실행이 겹쳐도 비용이 두 번 나가지 않는다.

채점이 전부 `pending`으로 나오는 것은 정상이다 — 5거래일이 아직 안 지났다는 뜻이고,
저울이 가짜 숫자 대신 "못 잼"을 돌려주고 있다는 증거다. 첫 실제 성적은
**09-22경(5일)**과 **10-14경(20일)**에 나온다.

## 2순위 — 수집이 장중에 계속 도는지

**수집 자동화는 끝났다.** 2026-09-16 `17:05 UTC` 정시 실행으로 launchd → 래퍼 →
수집기 → SQLite 쓰기까지 전 경로를 확인했다.

```
17:05:00Z  ───── 수집 시작 (pid 83986)
  대상 3 / 전체 30      ← 1h 주기 종목만 골랐다
  OK 삼성전자 10 · SK하이닉스 9 · NAVER 4
  3/3 성공 · 누적 5,957건
17:05:01Z  ───── 완료 (성공)
```

fetched 23 → inserted 13. 중복은 `(symbol, content_hash)` PK가 걸렀다. 소요 1초.

남은 건 **이게 계속 도는지**다. 새 세션은 여기부터 본다.

```bash
tail -20 logs/collect.log                    # 매시 기록이 쌓이는가
scripts/install_scheduler.sh --status        # last exit code = 0 인가
python scripts/collect_news.py --status      # 열린 gap 0건인가
```

**한국 장중(KST 09:00~15:30)에 시간 구멍이 없는지가 핵심이다.** 야간 구멍은 유입이
적어 다음 수집의 lookback이 메우지만, 장중 구멍은 1,000건 한도에 잘려 영구 손실이다.

이상 신호와 대응

| 증상 | 원인 | 대응 |
|---|---|---|
| 새 줄이 안 늘어난다 | launchd 미실행 | `--status`의 exit code, `logs/launchd.err.log` |
| `Operation not permitted` / `exit 126` | TCC | 저장소가 Desktop·Documents·Downloads 아래로 갔는지 |
| `SKIP 이전 수집이 아직 돌고 있다` | 앞 수집이 멈춤 | 30분 뒤 락이 자동 해제된다. 반복되면 벤더 응답 지연 의심 |
| `WARN 디스크 여유` | 10GB 미만 | 정리. 1GB 미만이면 수집을 아예 중단한다 |
| 장중에 몇 시간씩 비어 있다 | 노트북이 잠들었다 | 미결 1번(잠자기 한계) — 구조적 한계다 |

### 스케줄러 다루기

```bash
scripts/install_scheduler.sh                    # 두 작업 등록 / 재등록
scripts/install_scheduler.sh --status           # 상태와 마지막 종료 코드
scripts/install_scheduler.sh --run-now collect  # 즉시 1회 (launchd 경유)
scripts/install_scheduler.sh --run-now baseline # 이미 돌린 시점이면 비용 없이 건너뛴다

```

plist는 `~/Library/LaunchAgents/com.ys.mastrade.collect.plist`에 있다. 저장소 밖이라
git과 무관하고, 경로가 박혀 있으므로 **이사하면 반드시 재등록해야 한다.**

`scripts/run_collect.sh`는 자기 위치로 저장소 루트를 찾으므로 옮겨도 안 깨진다.

### 또 이사할 일이 생기면

1. **`mv`로 옮긴다. 다시 clone하지 않는다.**
   `data/mas_trade.sqlite3`와 `data/snapshots/`는 gitignore 대상이라 clone에 딸려오지
   않는다. 새로 받으면 **5,944건과 기록 시작점을 잃는다.** 다시 받을 수 없는 데이터다.
2. **venv를 다시 만든다.** shebang에 절대경로가 박혀 있다.
   ```bash
   rm -rf .venv && python3 -m venv .venv
   .venv/bin/pip install -r requirements.txt
   ```
3. **`.env`가 따라왔는지 확인한다.** gitignore 대상이다. 없으면 수집이 전부 실패한다.
   ```bash
   python scripts/smoke_test_apis.py    # 아래 주의 참고
   ```
   > **주의 — 새벽에는 DART가 거짓 실패한다.** 날짜 없이 당일 공시를 조회하는데
   > 공시가 없는 시간대면 `status=013`이 와서 FAIL로 찍힌다. 키 문제가 아니다.
   > 아직 안 고쳤다 (미결 2번, DART 스모크 테스트). 낮에 돌리면 8개 중 SEC만 실패하는 게 정상이다.
4. **`scripts/install_scheduler.sh`를 다시 돌린다.** plist 경로가 갱신된다.
5. 경로가 박힌 문서를 고친다 (`README.md`, 이 문서).

### 왜 급한가

피크(KST 16시경) 유입이 200건/h인데 한 번에 1,000건까지만 받을 수 있다.
→ **장중에 5시간 넘게 멈추면 그 앞은 영구 손실이다.**
야간 복구는 쉽고 주간 복구는 불가능하다. 장애 감지는 한국 장중을 기준으로 봐야 한다.

**launchd도 이걸 완전히 막지는 못한다.** 잠든 사이 밀린 실행은 깨어날 때 **한 번으로
합쳐진다.** 뚜껑 닫고 반나절 나가 있으면 그 사이 유입분은 1,000건 한도에 잘린다.
노트북으로 24시간 수집하는 건 구조적 한계다 (미결 1번, 잠자기 한계).

## 건드리기 전에 알아야 할 설계 결정

근거는 `docs/journal/2026-09-15.md`에 있다. **모르고 뒤집으면 데이터가 망가진다.**

| 결정 | 이유 |
|---|---|
| `INSERT OR IGNORE` (REPLACE 아님) | `collected_at`이 최초 관측 시각으로 고정돼야 `known_at`의 보수적 판정이 유지된다 |
| as-of 필터는 항상 `known_at` | `published_at`으로 거르면 벤더 시각이 깨졌을 때 룩어헤드가 샌다 |
| 실패한 수집은 `collection_runs`에 기록하지 않는다 | 기록하면 "방금 돌았다"로 판정돼 다음 주기까지 재시도하지 않는다 |
| lookback = 마지막 수집 이후 × 1.5 | 고정값은 평소 과하게 받고 장기 중단 뒤엔 못 메운다 |
| `relevance='summary'`도 버리지 않는다 | "스쳐 언급도 예측력이 있나"를 추가 호출 없이 사후 재채점하기 위해 |
| 영문은 단어 경계 + 대소문자 무시, 한국어는 부분 문자열 | 한국어는 조사가 바로 붙어 경계가 성립하지 않는다 (`SKT가`) |
| 원본 응답은 수집 1회 = 파일 1개 | 페이지별로 쓰면 파일명이 같아져 서로를 덮어쓴다 |
| 파괴적 스크립트는 dry-run이 기본 | `reclassify.py`의 잘못된 규칙이 5,009건에 적용되기 전에 잡혔다 |
| 정기 실행은 cron이 아니라 launchd | cron은 자는 사이의 실행을 건너뛰고 따라잡지 않는다. 노트북에서는 그게 곧 데이터 손실이다 |
| 저장소는 Desktop/Documents/Downloads 밖 | TCC가 launchd 실행을 거부한다(`exit 126`). 사용자 권한 LaunchAgent도 막힌다 — 2026-09-16 실측 |

## 미결 (급한 순)

1. **확신도 폭이 좁다** — 30건에서 0.42~0.62, 표준편차 0.067. 순위상관은 계산되지만
   검정력이 약하다. 기획서 9.1절이 확신도-수익 상관을 가장 중요한 지표로 꼽았으므로
   그대로면 그 지표가 힘을 못 쓴다. 표본을 더 쌓고 판단한다. **고치면 그 전후 성적을
   섞으면 안 된다**(기획서 7절 — 프롬프트 튜닝도 파라미터 튜닝).
   참고: 룰 기반 비교군의 확신도(폭 0.50~0.95)도 상관이 0 근처였다 —
   **이 지표 자체가 원래 잡기 어려울 수 있다**(`docs/baselines.md` 3.5)
2. **hold 비율 50%** — hold는 적중 판정에서 빠져 실효 표본이 절반이 된다.
   "3개월 150건"을 채우려면 실제로는 300건이 필요할 수 있다
3. **잠자기 한계 — 배터리에서는 여전히 취약하다.** `caffeinate -im`으로 **실행 중**
   잠드는 것은 막았지만(2026-09-17), 배터리에서는 시스템 잠자기를 막을 수 없다.
   뚜껑을 닫으면 launchd가 DarkWake로 깨워도 금방 다시 잠든다.
   **장중에는 전원을 연결하고 뚜껑을 열어두는 것이 사실상의 대책**이고,
   근본 해결은 상시 전원 기기로 옮기는 것이다
4. **DART 스모크 테스트 거짓 실패** — 날짜 없이 당일을 조회해 새벽엔 `013`이 온다
5. **디스크 여유 27GB / 87%** — 래퍼가 10GB 미만 WARN, 1GB 미만 ABORT
6. ~~감시자 자동화~~ — **기계적 판정은 붙였다** (2026-09-17). `scripts/health_check.py`가
   매일 08:30 KST에 돌며 이상 시 macOS 알림을 띄운다. 남은 것은 **해석**이다 —
   "왜 그런가"와 "무엇부터 고치나"는 아직 사람(또는 로컬 Claude 세션)의 몫
7. ~~층 2 가상 포트폴리오~~ — **구현했다** (2026-09-18). 룰 전략 3년치로 검증 완료.
   LLM 시그널은 1회차뿐이라 아직 못 돌린다 — 몇 주 쌓이면 같은 스크립트로 비교된다.
   결과와 한계는 `docs/baselines.md` 7절
